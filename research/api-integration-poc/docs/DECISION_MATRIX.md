# 技术选型矩阵与推荐

| 项目 | 内容 |
|---|---|
| 文档版本 | V1.0（初稿） |
| 日期 | 2026-11-17 |
| 依据 | `API_RESEARCH.md` 及其来源清单 |
| 性质 | 预研结论，不构成采购决定、报价或工期承诺 |

---

## 1. 总览

| 业务 | 推荐路线 | 一句话理由 |
|---|---|---|
| 社媒 | **官方 API 为主（方案 A 起步），预留聚合适配层；若 TikTok/X 为首日刚需则采用方案 C** | 首批渠道（FB/IG/LinkedIn/YouTube）官方能力完整，聚合主要买的是审核流程；TikTok/X 的审核与凭证负担最重，适合用聚合隔离 |
| 视频 | **托管与发布分层：独立视频托管（Mux 主候选）+ 各平台官方发布（方案 B 的视频部分）** | 没有任何一家可靠地同时做托管、转码与跨平台发布 |
| GA4 | **仅用 Google 官方 API** | 官方 API 已覆盖全部报表与配置需求，聚合无法解锁额外指标 |

## 2. 社媒选型矩阵

| 维度 | 官方 API/SDK（方案 A） | 聚合 API（方案 B） | 混合（方案 C） |
|---|---|---|---|
| 平台覆盖 | 取决于逐个申请，能力最完整 | 14–16 个平台，覆盖广但深度受聚合方实现限制 | 聚合覆盖长尾，官方覆盖核心 |
| 发布能力 | 完整（含平台特有格式） | 统一接口，但平台差异以选项对象暴露 | 核心平台用官方，长尾用聚合 |
| 数据分析能力 | 各平台原生指标最全 | 有统一分析，但字段与粒度受聚合方限制 | 报表以官方为主，聚合仅取基础数据 |
| OAuth 管理 | 每平台一套（2h/60d/60d/可刷新等差异大） | 统一托管，但客户仍需逐平台授权 | 核心平台自管，长尾交给聚合 |
| 视频上传 | 各平台分片/恢复流程 | 统一上传，但平台上限不同 | 同左 |
| 权限审核 | Meta Business Verification、LinkedIn Standard tier、TikTok 审核、YouTube audit | 聚合方持有已审核应用，可吸收大部分 | 核心平台自审，长尾由聚合承担 |
| 开发复杂度 | 高：5 套 OAuth + 5 套错误模型 | 中：1 套鉴权 + N 个平台分支 | 中高：两套体系并存 |
| 供应商费用 | 无 API 费（X 按量付费） | 按账号/套餐订阅，随客户数增长 | 订阅费 + 自建成本 |
| 运行成本 | 自建 token 刷新、重试、监控 | 聚合方承担基础设施，共享配额 | 两者都有 |
| 数据安全 | 数据不经过第三方 | 内容与 token 经聚合方中转，需 DPA | 核心数据自持，长尾经第三方 |
| 可扩展性 | 新增平台 = 新增应用与审核 | 新增平台通常只需配置 | 取决于接入位置 |
| 供应商锁定 | 低（平台锁定仍在） | 高（payload/错误模型抽象） | 中 |
| 后续维护 | 跟随平台版本升级 | 跟随聚合方版本，平台政策变化可能转嫁 | 双线维护 |

**推荐：方案 A 起步，架构上预留聚合适配层（即 C 的接入点）。**

- 首选官方：Facebook/Instagram（Meta）、LinkedIn、YouTube。理由是这三家的发布与统计是 B2B 独立站的核心链路，数据不经过第三方，且审核虽然慢但一次通过后长期有效。
- 预留聚合：TikTok 与 X。TikTok 未审核只能发私密、审核周期不可控；X 按量付费且从 2026-03-31 起聚合方案要求客户自备凭证。用 `SocialProvider` 接口隔离，二者可在不改业务层的前提下切换官方或聚合。
- 不选方案 B 全量聚合的原因：客户侧 OAuth 仍要逐平台完成，平台差异仍在；同时引入按账号计费、单点故障、共享配额与 payload 锁定，而 Morrishk 的渠道数量与账号规模不足以摊薄这些成本。
- 不选方案 A 全量直连的原因：TikTok/X 的非代码门槛可能拖住上线，且 X 的读取成本不可控。

**供应商退出方案**：业务层只依赖 `SocialProvider`（`connect / listAccounts / publish / getPost / fetchMetrics / disconnect`）；聚合实现与官方实现可互换；发布记录与平台返回的原始 ID 由本地保存，迁移时按 ID 回查，不依赖聚合方历史数据。

## 3. 视频选型矩阵

| 维度 | 官方/自建 | 聚合 API | 混合（推荐） |
|---|---|---|---|
| 平台覆盖 | 5 个社媒平台逐个接入 | 聚合商覆盖社媒，不覆盖托管 | 托管 1 家 + 社媒官方 |
| 发布能力 | 完整，含各平台限制处理 | 统一发布，视频上限仍按平台 | 托管母版，逐平台发布 |
| 数据分析能力 | 平台原生播放/互动数据 | 有限 | 托管侧播放分析 + 平台侧互动数据 |
| OAuth 管理 | 平台各自 OAuth | 统一 | 平台 OAuth + 托管 API Key |
| 视频上传 | 每平台分片/恢复 | 统一上传 | 托管分片上传一次，平台各自再传 |
| 权限审核 | 平台审核 | 聚合承担部分 | 同左 |
| 开发复杂度 | 高（5 套上传 + 转码自建） | 中 | 中（托管 SDK 成熟） |
| 供应商费用 | 自建存储/CDN 成本高 | 订阅费 | 按分钟计费（Mux/api.video） |
| 运行成本 | 转码与 CDN 运维重 | 由聚合承担 | 由托管商承担 |
| 数据安全 | 完全自持 | 经第三方 | 视频资产在托管商，需 DPA |
| 可扩展性 | 受自建容量限制 | 受聚合能力限制 | 高 |
| 供应商锁定 | 低 | 高 | 中（播放 ID/资产可导出） |
| 后续维护 | 重 | 轻 | 轻 |

**推荐**：

1. 托管主候选 **Mux**：直传、分片、Webhook、字幕轨、缩略图、播放分析齐全，接口模型清晰；备选 **api.video**（单价更低）与 **Cloudinary**（图片/视频统一治理）。
2. 社媒发布使用各平台官方接口，不与托管商绑定。
3. 站内播放使用托管商播放器/播放 ID；社媒侧按平台限制生成派生版本（LinkedIn 500MB/30 分钟、IG 300MB/15 分钟、TikTok 4GB/10 分钟）。

**退出方案**：母版文件保留在自有对象存储；托管商只作为转码与分发层，播放 ID 与资产元数据本地留档；切换托管商时重新转码并替换播放地址，社媒已发布内容不受影响。

## 4. GA4 选型矩阵

| 维度 | 官方 API | 聚合 API | 混合 |
|---|---|---|---|
| 平台覆盖 | GA4 全部属性 | 取决于聚合商 | 不必要 |
| 发布能力 | 不适用 | 不适用 | 不适用 |
| 数据分析能力 | 完整（报表/实时/透视） | 通常只封装常用报表 | 无增益 |
| OAuth 管理 | OAuth 或服务账号 | 聚合方托管 | 无增益 |
| 视频上传 | 不适用 | 不适用 | 不适用 |
| 权限审核 | 无平台审核；需 GA4 角色授权 | 需把属性授权给聚合方 | 无增益 |
| 开发复杂度 | 低（官方客户端库） | 低 | 无增益 |
| 供应商费用 | 免费（配额内） | 订阅费 | 更高 |
| 运行成本 | 配额按属性独立 | 共享配额 | 更高 |
| 数据安全 | 数据不经过第三方 | 经第三方 | 更差 |
| 可扩展性 | 按 Property 横向扩展 | 受聚合商支持范围限制 | 无增益 |
| 供应商锁定 | 低 | 高 | 中 |
| 后续维护 | 跟随 Google 版本 | 跟随聚合商 | 双重 |

**推荐：仅用官方 API。**

- 报表与实时数据：Data API，按 Property 独立配额。
- 资源发现与配置：Admin API（`accountSummaries.list` 枚举客户属性）。
- 服务端事件（询盘/报价）：Measurement Protocol 写入，再用 Data API 读回验证；不得把 MP 回执当报表。
- 多客户：单服务账号按 Property 授权（运维简单）或按客户 OAuth（隔离最强），二选一需客户确认。

**退出方案**：不涉及第三方，无需迁移；仅需管理 GCP 项目与服务账号密钥轮换。

## 5. 候选架构评估（方案 A / B / C）

| 评估项 | 方案 A：全部官方直连 | 方案 B：社媒全聚合 + 视频独立托管 + GA4 官方 | 方案 C：混合 |
|---|---|---|---|
| 审核负担 | 全部自担 | 社媒审核大部分由聚合承担 | 核心自担，长尾外包 |
| 开发量 | 最大 | 社媒最小，视频/GA4 不变 | 中 |
| 单点故障 | 无 | 社媒全部依赖一家 | 核心链路无单点 |
| 成本可预测性 | 高（X 除外） | 低（按账号/套餐） | 中 |
| 数据合规 | 最好 | 社媒内容经第三方 | 核心数据自持 |
| 上线速度 | 慢（审核） | 快 | 中 |
| 适配 Morrishk | 适合首批 3–4 个渠道 | 适合多客户、多平台代运营 | **最平衡** |

**结论**：社媒采用「方案 A 起步 + 预留方案 C 接入点」；视频采用方案 B 的分层结构；GA4 采用官方 API。三者不强行统一。

## 6. 实施前需客户确认的事项

| 编号 | 事项 | 影响 |
|---|---|---|
| D-1 | 首批发布渠道清单（FB / IG / LinkedIn / YouTube / TikTok / X 的优先级） | 决定官方直连范围与聚合是否需要 |
| D-2 | 各平台账号的所有权与管理员角色由谁持有 | 决定 OAuth 主体与审核申请方 |
| D-3 | 是否接受内容经聚合商中转（DPA、数据驻留） | 决定能否使用聚合 |
| D-4 | X 是否在首期范围；若在，是否接受按量付费与自备凭证 | 决定 X 接入方式与预算 |
| D-5 | TikTok 是否必须公开发布（而非私密/草稿） | 决定是否必须走 Content Posting 审核 |
| D-6 | 视频托管预算与用量预期（存储分钟、分发分钟） | 决定 Mux / api.video / Cloudinary |
| D-7 | GA4 采用「单服务账号 + 按 Property 授权」还是「按客户 OAuth」 | 决定隔离模型与运维方式 |
| D-8 | 多语言内容发布是否需要按语种分渠道 | 影响发布编排与内容模型 |
| D-9 | 排期由平台原生（YouTube/FB）还是自建调度统一承担 | 影响任务系统设计 |
| D-10 | 是否需要保存平台侧互动数据用于线索归因 | 影响分析接口范围与配额预算 |
