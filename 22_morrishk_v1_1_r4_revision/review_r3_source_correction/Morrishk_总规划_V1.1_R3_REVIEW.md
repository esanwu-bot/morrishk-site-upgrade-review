## 1. 项目目标与总体原则

### 1.1 项目目标

将现有 Morrishk 网站逐步升级为一套可持续运营的半导体电子元器件 B2B 平台，形成以下业务能力：

1. 产品主数据和产品详情管理。

2. 基于 Ds Bit 的 PDF 数据解析、参数抽取、证据管理和质量审核。

3. Ds Bit 向 Morrishk 提供经过审批的产品技术数据。

4. 产品目录、品牌、分类、参数、搜索和产品详情页面。

5. RFQ、询价、客户线索和销售跟进。

6. SEO、多语言、内容管理和网站运营。

7. 营销工作台、社交媒体和营销数据分析。

8. 后台权限、审核、任务、配置、审计和系统运维。

9. 旧网站数据、URL 和业务流程的兼容迁移。

### 1.2 总体架构边界

| 系统 | 职责 | 不负责的事项 |
| --- | --- | --- |
| Ds Bit | PDF 解析、技术参数、证据、质量审核、技术数据版本和发布状态 | Morrishk 的业务分类、询价和营销流程 |
| Morrishk | 产品业务主数据、目录、页面、询价、客户、SEO、营销和运营 | 自行推断或覆盖未经批准的技术参数 |
| Business API | Ds Bit 与 Morrishk 之间的身份、查询、证据和数据交换 | 替代 Ds Bit 内部解析和质量审核 |
| 数据同步层 | 获取已发布数据、幂等更新、失败重试、差异检查 | 绕过发布门槛直接发布产品数据 |

必须坚持：

• 技术分类与业务导航分类分离。

• 产品业务身份以规范化 (mpn_norm, brand_norm) 为核心，不能以 PDF 或 document ID 作为永久产品身份。

• prod-{document_id} 仅可作为临时文档流程标识。

• 原始 MPN、原始 Brand、规范化值和 normalizer 版本均应保留。

• 品牌缺失、MPN 冲突和身份歧义不能自动合并。

• 旧 URL、历史产品和询价记录必须纳入兼容方案。

• 产品详情页不得直接依赖 Ds Bit 在线解析；应使用本地已同步数据和缓存。

### 1.3 技术与发布状态原则

以下状态必须严格区分：

• PIPELINE_PASS：解析流水线通过。

• CONTENT_APPROVED：技术内容经过审核批准。

• RELEASE_APPROVED：数据获准向业务系统发布。

只有达到 RELEASE_APPROVED 的技术数据，才可以进入 Morrishk 正式产品展示数据。

以上 PHP 静态代码风险仍需在真正的 Morrishk 应用仓库中复核，并通过测试验证。Discovery 报告通过不代表这些问题已经修复，也不代表生产数据库已被访问或验证。

| --- | --- | --- | --- |
| P0 | 项目基线与安全治理 | 建立可恢复、可审计的开发和运行基线 | 待执行/待验证 |
| P1 | 架构与主数据治理 | 产品身份、分类、属性、权限和迁移规则明确 | 部分设计已有，决策待闭合 |
| P2 | Ds Bit 技术数据引擎 | 解析、审核、发布和 Business API 具备生产验收条件 | 设计阶段，未获生产批准 |

| P5 | SEO、多语言与内容运营 | 站点可被搜索引擎理解并持续运营 | 待需求确认 |

## 4. 分阶段任务规划

## P0：项目基线与安全治理

目标：先确保开发对象明确、代码可追溯、数据可恢复、敏感配置受控。不得在无法恢复的旧站上直接开展大规模改造。

### P0-01：确认真正的 Morrishk 应用仓库

• 优先级：P0

• 负责人：项目负责人 + 执行 Agent

• 前置：无

• 工作：

– 确认旧站代码实际所在仓库或服务器目录。

– 确认生产、测试、开发环境边界。

– 确认当前分支、HEAD、工作区状态和部署版本。

– 识别 morrishk-site-upgrade-review 与实际应用仓库的关系。

• 交付物：应用仓库与环境清单、Git 基线报告。

• 验收：仓库地址、分支、提交 SHA、运行环境均有可复核证据。

• 状态：BLOCKED / UNVERIFIED，等待真实应用仓库和环境确认。

### P0-02：建立 Git 和可恢复备份

• 优先级：P0

• 前置：P0-01

• 工作：

– 对旧站代码建立受控 Git 基线。

– 对数据库和上传文件建立一致性备份。

– 记录备份时间、文件大小、校验值和恢复步骤。

– 在隔离环境进行一次恢复演练。

• 交付物：代码基线、数据库备份、文件备份、恢复演练记录。

• 验收：能够从备份恢复到隔离环境，并验证关键业务表和文件。

• 状态：MISSING / UNVERIFIED。

### P0-03：生产配置与安全入口治理

• 优先级：P0

• 前置：P0-01

• 工作：

– 检查 YII_DEBUG、YII_ENV 等环境配置。

– 清理硬编码 SMTP、数据库和 cookie 签名密钥。

– 使用环境变量或受控 Secret 管理配置。

– 检查后台控制器认证与授权。

– 检查 CSRF 保护策略。

– 检查邮件发送接口是否存在未授权中继风险。

• 交付物：安全配置清单、风险整改记录、认证和授权测试。

• 验收：生产配置不暴露调试模式和明文凭据；未授权请求无法执行管理操作。

• 状态：MISSING / UNVERIFIED。

### P0-04：旧站风险复现与整改优先级

• 优先级：P0

• 前置：P0-01

• 工作：

– 对 Discovery v1.0.1 中的 PHP 静态发现逐项复核。

– SQL 拼接风险采用输入到 SQL 的调用链证据验证，不以静态字符串直接认定漏洞已被利用。

– 复核 FE-8 路由问题。

– 复核邮件、询价、购物车、后台和缓存问题。

• 交付物：风险复核矩阵、最小复现用例、修复任务。

• 验收：每项风险均有 EXISTS、FIXED、NOT_REPRODUCED 或 UNVERIFIED 结论。

• 状态：PARTIAL，已有静态审计材料，缺少完整动态复核。

### P0-05：项目环境和发布流程

• 优先级：P1

• 前置：P0-01、P0-02

• 工作：

– 建立开发、测试、预发布、生产环境配置边界。

– 明确部署审批、回滚、日志和告警流程。

– 建立数据库变更审查和备份要求。

• 验收：一次测试环境部署和回滚演练成功。

## P2：Ds Bit 技术数据引擎与 Business API

目标：使 Ds Bit 形成可验证、可审计、可发布的技术数据供应链，再通过冻结的 Business API 提供给 Morrishk。

### P2-01：Session A 设计决策闭合

• 优先级：P0

• 前置：P1-01、P1-04

• 工作：

– 以 Session A v1.16.1 为设计基线。

### 6.1 状态定义

• EXISTS：代码或文档已存在，且有证据。

• PARTIAL：只完成部分范围。

• MISSING：确认尚未实现。

• BLOCKED：被未完成的决策或依赖阻塞。

• UNVERIFIED：有报告或口头声明，但尚未独立验证。

• IN_PROGRESS：已经授权并正在执行。

• PASS：验收条件全部满足。

• FAIL：验收条件不满足。

不得把 UNVERIFIED 写成 EXISTS，不得把 PASS_MOCK 写成生产 PASS。

## 17. 旧域名与 URL 迁移

旧域名、旧 URL 和既有收录是项目最重要的 SEO 资产。迁移方案必须先盘点、后映射、再验证；未取得旧 URL 数据前，不得声称映射完成，也不得承诺迁移后排名、收录或流量不下降。

| 序号 | 工作项 | 输出/验收 |
| --- | --- | --- |
| 1 | 旧域名、DNS、SSL、CDN 管理关系 | 域名与账号归属表；证书/CDN 责任方 |
| 2 | 旧 URL 清单获取 | URL 清单、来源、数量、状态 |
| 3 | 旧 URL 与新 URL 映射规则 | 映射台账；人工确认记录 |
| 4 | 商品/品牌/分类/内容迁移策略 | 按页面类型的迁移方案 |
| 5 | 301 规则 | 仅语义等价；无链式；版本化清单 |
| 6 | Canonical 规则 | 绝对 URL、自指、规范 URL |
| 7 | Hreflang 与语言发布条件 | 第一阶段 en 不输出任何 hreflang（含 x-default）；第二语言真实发布后再互指，x-default=en |
| 8 | Sitemap 更新 | 只含规范、可索引 URL；分片/增量 |
| 9 | Robots 与索引控制 | 不屏蔽需读取 noindex 的页面 |
| 10 | 404/软 404/重定向链/循环检查 | 回归报告；软 404 为 0 |
| 11 | 上线前全量盘点、关键URL核验与分层抽样 | 全量清单；关键URL 100%核验；其余按规模分层抽样；状态码/title/H1/canonical |
| 12 | 上线后搜索表现与抓取监测 | GSC/日志报告；异常清单 |
| 13 | 异常处理与回滚 | 回滚预案、责任人、触发条件 |

URL 回归规模不再写死固定条数，按实际旧 URL 总量分层确定：

| 旧 URL 总量 | 全量盘点 | 关键 URL 核验 | 其余抽样建议（待负责人确认） |
| --- | --- | --- | --- |
| ≤1,000 | 100% | 100% | 100% |
| 1,001–10,000 | 100% | 100% | ≥30% 且不少于 1,000 |
| 10,001–100,000 | 100% | 100% | ≥5,000 或按类型分层抽样 |
| >100,000 | 100% | 100% | ≥10,000 + 按类型/流量分层抽样；关键 URL 始终 100% |

关键 URL 至少包括首页、主要分类/品牌页、重点产品页、主要落地页、历史上高流量 URL、已有外链 URL、所有计划 301 的源 URL。抽样规则、样本量和置信口径需项目负责人/客户确认，不构成固定验收数量。

• 原有 URL 能保留的尽量保留；不得仅凭分类名称相似自动建立 301。

• 分类映射变化不得自动触发 URL 变更或 301；必须人工确认语义等价。

• 旧 URL 清单、映射台账、回归结果均作为交付物，归客户所有。

• 本方案不承诺迁移后的排名、收录或流量结果。

## 18. 数据统计与询盘归因

询盘统计必须区分访问、商品浏览、询价点击、表单开始、提交成功、联系方式点击、来源渠道、落地页、产品/MPN、国家/地区和询盘状态。事件命名与字段一次定义、全站复用。
