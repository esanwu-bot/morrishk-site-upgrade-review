## 版本修订说明（v1.0 → v1.1）

本次修订只做一件事：**把项目目标从"技术升级"校准为"获客渠道"**，并据此重排资源投入顺序。技术能力本身没有删减，只是改变了先后与定位。

| # | 变更项 | v1.0 的写法 | V1.1 的写法 | 修订原因 |
|---|---|---|---|---|
| 1 | 项目定位 | 以技术能力为主线（稳 / 快 / 收得进 / 体验 / 智） | 以获客为主线（详情页 + 引流 + 询盘），技术作为支撑 | 老板明确：先做成能持续获取询盘的渠道 |
| 2 | 优先级模型 | 三期推进：修底座 → 提效率 → 要增长 | **P0 / P1 / P2 三层**，资源按"离询盘的距离"分配 | 让首期资源集中在能直接带来询盘的事上 |
| 3 | BOM 智能匹配 | 第三期旗舰功能之一（BOM 一键配单、平替推荐、参考报价） | **移出主线，降为 P2 可选模块**，前期只保留 BOM 上传的询盘入口 | BOM 涉及供应链数据、工程判断与商业规则，不适合作为首期阻塞项 |
| 4 | AI Agent 工作台 | 第三期旗舰功能（含大客户私域门户） | **P2**，待流量与询盘数据积累后再规划 | 同上；先有客户，再有 Agent |
| 5 | Ds Bit 参数解析 | 与搜索、SEO 并列的技术目标 | **服务于详情页**，按"高流量、高价值、有 PDF、有询盘潜力"优先覆盖 | 避免为技术而技术，参数是为了让详情页更值得被搜到、被相信 |
| 6 | 验收口径 | 页面数、解析 PDF 数、外链数 | **产品页访问量、询盘转化率、有效询盘数、渠道贡献** | 用商业结果衡量，而不是用交付件数量衡量 |
| 7 | 新增章节 | — | 第六章「询盘转化」、第十二章「验收指标」 | 原方案把询盘当成详情页的附属功能，没有单独设计 |

> 一句话总结：**v1.0 是一份"能力清单"，V1.1 是一份"获客路线图"。**

## 一、执行摘要

### 1.1 一句话结论

**先把 morrishk.net 做成一个能持续产生询盘的渠道，再谈半导体技术平台。**

具体讲：**产品详情页承接搜索流量，外部链接和社媒带来新增流量，询盘系统完成转化**——这三件事构成第一阶段的主线，其余能力围绕它们展开。

### 1.2 项目优先级（P0 / P1 / P2）

| 优先级 | 工作内容 | 核心目的 | 是否首期交付 |
|---|---|---|:-:|
| **P0** | 产品详情页升级 | 提升产品页的信息质量与询盘转化率 | ✓ |
| **P0** | 外链与社媒引流 | 获取外部流量，导入产品页与询盘入口 | ✓（运营先启动） |
| **P0** | 询盘路径优化 | 让客户更容易提交型号、数量与需求 | ✓ |
| **P1** | 搜索与 SEO | 提升产品页的自然搜索曝光 | ✓（与 P0 并行推进） |
| **P1** | Ds Bit 参数解析 | 提高详情页参数完整度与可信度 | ✓（分批，按重点产品） |
| **P2** | BOM 智能匹配 | 后续增值功能，不阻塞前期上线 | ✗ |
| **P2** | AI Agent、Cross Reference | 待流量与询盘数据积累后再规划 | ✗ |

**关于「引流」的阶段口径（重要）**：P0 中的「外链与社媒引流」指的是**运营动作在首期启动**，不代表发布队列、审计、视频管理等自动化系统也在一期交付。

- 一期：人工运营 + 内容模板 + UTM + 外链基础提交 + 社媒内容发布
- 二期：社媒系统化分发（队列、适配器、审核、幂等与尝试记录）+ 视频管理 + 渠道报表

技术版 Phase 1 / Phase 2 的分界与此一致。

**这张表的读法**：P0 决定"客户能不能找到我们、敢不敢问我们"；P1 决定"能不能被搜到、参数够不够硬"；P2 是有了客户之后才值得投的增值能力。

**与技术附件《详细技术方案 V1.2》的阶段对应**（两份文档口径一致，只是分法不同）：

| 本方案 | 技术方案 | 说明 |
|---|---|---|
| P0 | Phase 1（获客基础）+ Phase 2（流量增长） | 一期交付**运营动作**：内容模板、UTM、外链基础提交、社媒内容可开始发布；二期交付**软件系统**：发布队列、幂等与审计、视频管理、渠道报表 |
| P1 | Phase 2（搜索/SEO）+ Phase 3（参数数据能力） | 参数化 B1 跟随详情页上线，全量扩量由数据决定 |
| P2 | Phase 4（智能化与扩展） | 单独立项，不占首期资源 |

### 1.3 为什么这样排

老站已经有 **1,009 万个产品详情页**、982 个分类、1,427 个品牌、56.9 万份去重 PDF。这些资产的问题不是"没有"，而是"没有被用好"：

- 详情页内容薄、同质化，谷歌收不进，客户看一眼就走；
- 站外几乎没有可被引用的资产，流量来源单一，只能等自然搜索；
- 询盘链路存在，但没有被当作一个"产品"来设计，也没有被度量。

所以第一阶段不需要新平台，需要**把已有的千万级资产重新组织成"能被搜到、能被相信、能直接下单询问"的形态**。这三件事做完，才谈得上 BOM 与 Agent。

### 1.4 为什么不重写老站

| 重写的诱惑 | 现实代价 |
|---|---|
| 新框架、新界面、看起来更现代 | 约 **1009 万个产品详情页**已运行多年，换 URL 就要全量 301，排名与流量存在不可控的下滑 |
| 开发可能更快 | 后台、询价、发信、80 个语种入口都要重做，周期与预算远高于原地升级 |
| 技术栈更新 | 数据是 2024-11-30 的静态终态，不需要新框架的写入能力，重写带不来对等收益 |

**结论：原地升级，URL 不动，数据不动，能力逐块替换。**

### 1.5 第一阶段要交付的三件事

| 环节 | 客户能感知到什么 | 衡量方式 |
|---|---|---|
| **① 产品详情页** | 打开任意重点型号，能看到完整参数、Datasheet、相关型号，询价按钮一眼可见 | 产品页访问量、页均停留、详情页→询价点击率 |
| **② 外部引流** | LinkedIn / Reddit / YouTube / 行业目录上开始出现 morrishk 的内容，且每条都能追踪 | 各渠道带来的会话数与询盘数 |
| **③ 询盘转化** | 客户可以单型号询价、多型号批量询价、上传 BOM，提交后有明确回执 | 询盘提交数、有效询盘数、响应时长 |

### 1.6 收益预期（预估，非承诺）

按"离询盘的距离"分两类看，避免把慢变量混进快变量里。

**A 类：直接影响询盘（P0，3–6 个月可见）**

| 杠杆 | 作用机制 | 观察口径 |
|---|---|---|
| 详情页重构 | 参数、资料、相关型号齐全，客户不必跳走 | 详情页→询价点击率、页均停留 |
| 询盘路径简化 | 少填字段、支持多型号与 BOM 上传 | 询盘提交数、表单放弃率 |
| 社媒 + 视频引流 | 站外带来新会话，落到产品页 | 渠道会话数、渠道询盘数 |
| 行业目录与外链 | 带来精准参考流量与品牌可信度 | 引荐流量、引荐询盘数 |

**B 类：放大上限（P1，6–12 个月起复利）**

| 杠杆 | 作用机制 | 观察口径 |
|---|---|---|
| 搜索容错与分面 | 错字、中缀、带空格都能命中 | 挽回约 **20%–30%** 的搜索流失（行业经验区间，以搜索日志为基线校准） |
| 结构化数据 | 谷歌结果可展示参数、库存、询价 | 富结果点击率、收录量 |
| 参数化覆盖 | 重点产品页内容变厚，长尾词可承载 | 参数覆盖率、被收录页数 |
| 五语种 SEO | hreflang + 本地化内容 | 新增语种市场曝光 |

**说明**：以上为方向性预估，用于判断投入优先级，不构成效果承诺。项目启动后先建立基线，再按真实数据校准。

### 1.7 需要客户拍板的四件事

1. **其余 75 个存量语种域名**如何处置（保留可访问 / 收敛）。
2. **276 万条"隐藏"商品**是否继续对外可见。
3. **PDF 与产品图片**的授权与资产归属。
4. **社媒账号与视频素材**由谁提供、归谁所有、谁审核。

## 二、老站现状体检

> 以下数据来自对线上站点、数据库与日志的只读核查（2026-11-13），不含任何推测。

### 2.1 站点基本盘

| 项 | 现状 | 含义 |
|---|---|---|
| 架构 | PHP + Yii2 单体应用 | 成熟稳定，但缺少现代化检索与结构化数据能力 |
| 产品数据 | **10,093,684 条** | 千万级长尾，是最大的 SEO 资产 |
| 分类 | 982 个 | 三级分类体系完整 |
| 品牌 | 1,427 个 | 品牌页具备独立排名潜力 |
| 文章 | 183 篇 | 内容基础偏薄 |
| PDF 资料 | 约 563 万条商品关联 PDF，去重后 **568,830 个** | 参数化的原料充足 |
| 详情缓存 | 31.7GB | 详情页读取快，但维护成本高 |
| 整库备份 | 47.8GB | 迁移与重建必须分批、限速 |
| 语种入口 | 80 个域名 | 实际正式运营 5 个语种 |
| URL 形态 | 全部以 `.html` 结尾，详情页为"8 位编号 + 型号名" | **不可变更的 SEO 生命线** |
| 分析工具 | GA4、GTM、Yandex、Clarity 已安装 | 有数据底座，但缺少事件规范与归因 |

### 2.2 千万级数据资产盘点

| 数据类别 | 规模 | 质量判断 | 处置方向 |
|---|---|---|---|
| 正常在售商品 | 约 733 万 | 可索引主体 | 进入主 sitemap 与搜索索引 |
| 标记为"隐藏"的商品 | 约 **276 万** | **前台仍可访问** | 可回收的流量资产，需制定可见性策略 |
| 无 PDF 的商品 | 约 446 万 | 无法做参数表 | 保留页面，参数沿用现有字段 |
| 有 PDF 的商品 | 约 563 万 | 可参数化 | 去重后按优先级解析 |
| 停产商品 | 待精确统计 | 仍有长尾价值 | 页面保留，标注停产，搜索降权 |
| 异常状态 | 59 条 | 脏数据 | 从索引与地图中排除 |

**判断**：数据不是"不能用"，而是"没有被结构化"。一旦把 56.9 万个 PDF 变成标准参数，详情页的内容厚度和可检索性会立刻上一个台阶——**这也是为什么 Ds Bit 要服务于详情页，而不是自成目标**。

### 2.3 搜索体验实测（最直观的痛点）

我们用工程师最常见的输入方式，对线上搜索做了实测：

| 输入方式 | 例子 | 网站当前反应 | 用户感受 |
|---|---|---|---|
| 完整型号 | M4T28-BR12SH1 | 正常出结果 | 可用 |
| 小写型号 | m4t28 | 正常出结果 | 可用 |
| **错一个字符** | M4T28-BR12SH2 | **直接跳到询价车** | "这站是不是没有？" |
| **只输入中段** | BR12SH1 | **直接跳到询价车** | "明明有货却搜不到" |
| **带空格** | M4T28 BR12SH1 | **直接跳到询价车** | "太难用了" |

**结论**：当前搜索只认"从第一个字符开始完全正确"。这不是优化问题，是能力缺失。对一个千万级料号库来说，等于把大量本可成交的流量直接推走。

### 2.4 详情页与内容质量

| 项 | 现状 | 影响 |
|---|---|---|
| 参数表 | 只来自一个历史 JSON 字段，覆盖参数有限 | 页面内容薄，同质化严重 |
| 结构化数据 | 无 | 谷歌无法识别"这是产品"，拿不到富结果 |
| PDF | 外链第三方域名，可用但不受控 | 可做参数化，但长期需自有托管 |
| 产品图片 | 部分历史图片资源缺失或托管异常 | 影响转化、社媒分享卡片与图片搜索 |
| 相关型号 | 关联关系弱 | 客户看完一个型号就走了，没有形成浏览深度 |
| 页面标题 | 型号 + 品牌 + 站点后缀 | 可读，但未针对搜索意图分层 |

### 2.5 询盘与转化现状

| 项 | 现状 | 影响 |
|---|---|---|
| 询价入口 | 详情页表单 + 购物车批量询价 | 链路存在，但两条路径割裂，客户常不知道走哪条 |
| 表单字段 | 沿袭早期设计，字段偏多 | 移动端填写成本高，放弃率不明 |
| BOM 需求 | 只能靠邮件往返，人工逐行查 | 大单响应慢，且无法沉淀为数据 |
| 线索落地 | 提交后以邮件通知为主，无统一线索库 | 无法统计"收到多少、跟了多少、成了多少"（口径待与销售侧核对） |
| 有效询盘判定 | 无标准 | 询盘数量与真实采购需求混在一起，无法评估渠道质量 |
| 归因 | 无 UTM 规范，无服务端回传 | 不知道询盘从哪个渠道来，无法决定加码或停投 |

**判断**：这是当前最被低估的一块。**流量再好，如果询盘链路没有被设计过、没有被度量过，获客就永远是"感觉有效"。**

### 2.6 站外资产与流量来源现状

| 项 | 现状 | 影响 |
|---|---|---|
| 自然搜索 | 主要流量来源 | 单一渠道，谷歌算法波动直接传导到询盘量 |
| 社媒账号 | 无系统运营 | 工程师与采购聚集的 LinkedIn / Reddit 上没有存在感 |
| 视频 | 无 | 缺少"看得见产品"的内容形态，YouTube 搜索红利未吃 |
| 行业目录 / B2B 平台 | 基本空白 | 缺少基础信任背书 |
| 外链 | 接近为零 | 域名信任度低，抓取优先级低 |
| 技术内容 | 183 篇文章，以公司动态为主 | 缺少可被行业引用的选型/对比类内容 |

**判断**：站内是千万级资产，站外接近真空。**这个反差本身就是最大的增长空间**——不需要创造新内容，只需要把已有的参数能力变成外部愿意引用的东西。

### 2.7 稳定性与运维复盘

**502 的根因链已经查清**：站点与多个高流量站点共用同一台服务器与同一块磁盘；访问日志长期未轮转，单文件涨到 GB 级；磁盘写满后，数据库与 Web 服务无法写入临时文件，最终表现为 502。

**当前状态**：

- 已补充日志轮转，属于应急止血。
- 磁盘当前使用 58%，短期安全。
- 但 PHP、数据库、应用日志尚未纳入统一轮转，也没有磁盘与服务告警。
- 数据库仍使用旧式表引擎，写入时会锁表，高峰期存在排队风险。

**判断**：这不是"修一次就好"的问题，需要把应急措施变成可监控、可告警、可演练的常态。**获客的前提是站点不宕机**——宕机一次，当天的投放与内容全白做。

### 2.8 多语言现状

| 语种 | 现状 | 工作量 |
|---|---|---|
| 英文 | 主站，内容完整 | 维护 |
| 德文 / 日文 / 西班牙文 / 印尼文 | 词库已完整翻译，域名已存在 | 补新增词条 |
| 其余 75 个语种域名 | 可访问，但内容与运营投入有限 | 先盘点，再决定保留或收敛 |

当前的语言切换只在页脚做了一个下拉，搜索引擎无法据此识别"这是同一页面的不同语言版本"。这是五语种方案要补的第一块。

### 2.9 SEO 体检

| 检查项 | 现状 | 机会 |
|---|---|---|
| sitemap | 不存在 | 千万级页面缺少统一入口，抓取效率低 |
| canonical | 未输出 | 参数页、重复路径可能分散权重 |
| hreflang | 未正确输出 | 多语种无法互相背书 |
| JSON-LD | 无 | 无法进入产品富结果 |
| 404 | 不存在的产品返回"200 + 一段文字" | 软 404 会消耗抓取预算 |
| 分页 | 无上一页/下一页标记 | 深层列表抓取效率低 |
| robots | 规则存在重复与冲突 | 需要整理，避免误伤 |

**判断**：老站不是"没有 SEO"，而是"只有 URL 和标题这一层 SEO"。结构化的红利基本没吃。

### 2.10 安全与合规（概述）

体检中发现部分历史遗留的配置管理、权限控制与输入校验问题，以及生产环境调试开关未关闭等情况。这些问题不影响当前业务运行，但属于必须优先处理的风险项。

**处置原则**：统一纳入底座加固清单，按优先级逐项处理，细节在技术附件中说明，不在本商业方案中展开。

### 2.11 体检结论：保留 / 替换 / 新增

| 类别 | 对象 | 结论 |
|---|---|---|
| **保留** | 域名、URL 结构、产品数据、分类体系、品牌页、文章 | 一字不改，保住收录 |
| **替换** | 站内搜索、详情页参数来源、详情缓存构建方式、询盘表单与线索落地方式 | 换引擎、换数据源、换链路，不换 URL |
| **新增** | 结构化数据、sitemap、canonical/hreflang、五语种站点、社媒/视频分发、UTM 与归因、线索库 | 增量能力，独立开关 |

## 三、升级蓝图

### 3.1 三条铁律

1. **URL 不改**：除协议、主机名、大小写的规范化跳转外，不改任何既有路径。
2. **框架不换**：继续使用现有应用与服务器，避免千万级页面迁移。
3. **一切可回滚**：每个新能力都有开关；每次切换都有回退路径。

### 3.2 目标架构

```
        80 个语种域名
              │
      ┌───────▼────────┐
      │ 接入层          │  限速 · 缓存 · 规范化 301
      └───────┬────────┘
              │
      ┌───────▼──────────────────────────────┐
      │ 老站应用（URL 规则保持不变）           │
      │  · 详情页 → 新版缓存（含参数）  P0     │
      │  · 询盘   → 线索库 / 邮件 / 回执  P0   │
      │  · 搜索   → 精确型号直查          P1   │
      │  · 搜索   → 智能检索引擎          P1   │
      │  · 页面   → 预生成结构化数据      P1   │
      │  · Agent  → 参数问答 / BOM 配单   P2   │
      └───────┬──────────────┬───────────────┘
              │              │
      ┌───────▼──────┐  ┌────▼─────────────┐
      │ 业务数据库    │  │ 智能检索引擎      │
      │ 主数据只读    │  │ 版本化索引+别名    │
      │ 新参数/新缓存 │  └──────────────────┘
      │ 询盘线索库    │
      └───────┬──────┘
              │
      ┌───────▼──────────────────────────┐
      │ 离线流水线（独立机器，可中断）     │
      │ 数据清洗 → 索引构建               │
      │ PDF 下载 → 参数解析 → 质量门      │
      │ 结构化数据/静态缓存生成            │
      └──────────────────────────────────┘

      站外：LinkedIn / Reddit / X / YouTube / 行业目录 ──UTM──▶ 详情页
```

**设计要点**：所有重活（千万条索引、56.9 万个 PDF 解析）都在独立环境离线完成，不与线上抢资源；站外流量统一带 UTM 落地到详情页，形成"引流—承接—转化"闭环。

### 3.3 底座保障：稳定性与安全（与 P0 并行，不单独占期）

| 动作 | 说明 | 交付标准 |
|---|---|---|
| 日志治理 | 网站、PHP、数据库、应用四类日志统一轮转、压缩、保留 | 单文件不再无限增长 |
| 容量告警 | 磁盘、inode、5xx、证书、数据库连接 | 阈值触发邮件/IM 告警 |
| 备份演练 | 每日备份 + 每周快照 + 每月真实恢复演练 | 备份"能用"，而不只是"有" |
| 任务隔离 | 索引构建、PDF 解析放到独立环境 | 线上响应不受批处理影响 |
| 高负载保护 | 限速、超时、慢查询治理、后台入口保护 | 高峰期不雪崩 |
| 安全加固 | 关闭生产调试、轮换密钥、收敛后台入口、补输入校验 | 无堆栈泄露、无明文密钥 |

**业务结果**：不再因为日志或磁盘问题丢单；出问题能提前知道，而不是等客户投诉。**这是 P0 的隐含前提——引流一旦开始，站点必须扛得住。**

### 3.4 新老并行，而不是一刀切

- 新详情页、新搜索、新询盘表单都通过开关控制。
- 按分类、按流量比例逐步放量。
- 出现异常，分钟级切回旧逻辑，用户无感。
- 旧数据、旧页面、旧缓存保留一个完整观察期，不做不可逆删除。

## 四、P0-1：产品详情页升级

> 这是整个项目的**主战场**。产品详情页既是搜索流量的落地页，也是询盘的入口；一页之内要同时完成"讲清楚这颗料"和"让客户马上能问"。

### 4.1 现状与差距

| 维度 | 现状 | 差距 |
|---|---|---|
| 型号与品牌 | 标题有，但结构不清晰 | 客户第一眼要确认"是不是这颗料" |
| 产品分类 | 有面包屑 | 层级理解与内链引导不足 |
| 参数表 | 字段有限、无单位规范 | 工程师无法据此判断能否用 |
| Datasheet | 外链第三方 | 可用但不可控，且无下载统计 |
| 相关型号 | 关联弱 | 没有形成"同系列/可替代"的浏览路径 |
| 应用信息 | 基本没有 | 缺少"这颗料用在哪"的内容 |
| 询价入口 | 有表单 + 购物车 | 不突出、路径割裂、无多型号能力 |

### 4.2 页面信息结构（模块清单）

按"客户从上到下看什么"排序，而不是按数据库字段排序：

| 顺序 | 模块 | 内容要求 |
|---|---|---|
| 1 | 标题区 | 型号（最大）、品牌、封装/关键属性一行的摘要 |
| 2 | 核心状态 | 库存状态、是否停产、数据截止日期 |
| 3 | **询价区（首屏可见）** | Request a Quote 主按钮 + 加入询价清单 + 数量输入 |
| 4 | 关键参数表 | 6–12 个决策参数（封装、安装方式、电压、电流、温度、RoHS 等） |
| 5 | 完整参数表 | 折叠展开，按类别分组，带单位 |
| 6 | Datasheet | 在线预览 + 下载按钮（下载计入事件） |
| 7 | 相关型号 | 同系列 / 同封装 / 可替代候选（标注"需工程师确认"） |
| 8 | 应用与说明 | 典型应用、注意事项（有内容才展示，不编造） |
| 9 | 视频（有则展示） | 产品实拍、封装对比 |
| 10 | 底部询价区 | 同 3，减少客户回滚成本 |

**原则**：**询价入口首屏可见 + 底部复现**。不要让客户"看完参数再往上滚去找按钮"。

### 4.3 参数表与 Datasheet

- **参数来源分级**：Datasheet 解析结果 > 现有结构化字段 > 人工补录。每条参数标注来源与更新时间。
- **只展示可信数据**：未通过质量门的参数只做展示、不进入结构化数据，避免被谷歌判定为不实内容。
- **单位统一**：V / mA / Ω / pF / ℃ 等统一换算，原始值保留可查。
- **Datasheet 可控**：优先自有托管 + CDN，逐步替换第三方外链；保留原链接作为兜底。
- **不虚构**：查不到的参数宁可不显示，也不用相近型号顶替。

### 4.4 相关型号与应用信息

- **同系列**：同品牌同系列的其他型号（自动关联）。
- **同规格**：同封装、同关键参数的横向对比入口。
- **可替代候选**：标注为"工程候选建议"，并**并列关键参数差异**，明确提示需台架验证（P2 阶段再升级为自动 Cross Reference）。
- **应用内容**：优先覆盖有流量的重点型号，不追求全量。

### 4.5 询价入口（与第六章联动）

详情页上的询价动作分三种，均不跳转、不打断浏览：

1. **单型号询价**：填数量 + 需求说明，30 秒内可提交。
2. **加入询价清单**：连续浏览多个型号后一次性提交（保留现有购物车能力，但入口前移）。
3. **上传 BOM**：跳转到询盘页的上传入口（见 6.2）。

### 4.6 视觉、移动端与性能

基于现有 UI 原型（首页、产品列表、详情、品牌、文章、文章详情）逐页替换。

| 改造点 | 说明 |
|---|---|
| 视觉体系 | 统一配色、字体、间距、卡片与按钮 |
| 移动端 | 单手可操作，图片不抖动，表单更短，询价按钮吸底 |
| 性能 | 首屏更快，JS 更轻，图片走 CDN |
| 可读性 | 参数表在移动端不横向溢出，改为卡片式 |

**红线**：换肤不改 URL、不改标题层级、不删内链、不改表单字段名。视觉可以新，SEO 骨架必须原样。

### 4.7 交付标准

- 重点型号（首批对应 1–2 万份文档的型号范围）详情页具备：参数表 + Datasheet 入口 + 相关型号 + 首屏询价。
- 移动端 Lighthouse 性能分不低于改造前基线。
- 详情页→询价点击率可被统计（事件埋点齐全）。
- 老 URL 抽样回归全部通过。

## 五、P0-2：外部引流（社媒 + 视频 + 外链）

> 这一章解决的不是"网站好不好用"，而是"客户从哪里来"。老站升级是地基，社媒与视频是持续引流的水管。

### 5.1 渠道分工

| 渠道 | 角色 | 主要产出 |
|---|---|---|
| LinkedIn | 行业见解、选型对比、供应链观察 | 精准 B2B 流量与品牌可信度 |
| Reddit / 技术社区 | 硬核答疑、替代料讨论 | 工程师信任 + 长尾自然流量 |
| X / Facebook | 库存快讯、交期提醒、新品上架 | 触达存量关注者 |
| YouTube | 实拍、封装对比、选型避坑 | 视频搜索曝光 + 站内停留 |
| 行业目录 / B2B 平台 | 企业资料与品类页 | 基础信任 + 参考流量 |
| 技术文章 / 合作伙伴 | 可被引用的参数与对比内容 | 编辑性外链 |

**共同原则**：所有站外链接统一带 UTM，全部落到**产品详情页或询盘页**，不落首页。

**第一阶段先跑"人工 + 模板"**：目录提交、社区答疑、内容发布由运营按模板执行，系统只提供文案草稿与 UTM 生成器；社媒分发器、视频批处理等自动化能力随后接入。**引流不必等系统建好才开始**——这也是它被列进 P0 的原因。

### 5.2 社媒矩阵（不增加人力负担）

电子元器件是 B2B 专业领域，不需要在娱乐平台跳舞，而要精准覆盖**工程师与采购决策者**。

**内容中台：一次编辑，多平台适配。** 客户在后台发布或更新产品时，系统自动抓取核心信息（型号、品牌、分类、关键参数、库存/交期），生成适配不同平台的文案：

| 平台 | 内容定位 | 示例方向 |
|---|---|---|
| LinkedIn | 行业见解、选型对比、供应链观察 | "同系列三个型号怎么选？一张表看懂" |
| Reddit | 硬核技术讨论、答疑 | "这颗料的替代型号与封装差异" |
| X / Facebook | 库存快讯、交期提醒、新品上架 | "M4T28 系列现货，支持小批量" |
| YouTube | 实拍、封装对比、选型避坑 | 1–3 分钟短视频 |

**分发方式：自动 + 半自动结合**

| 方式 | 适用 | 说明 |
|---|---|---|
| 官方 API 自动分发 | 有开放发布权限的平台与账号 | 后台一次编辑，多平台推送 |
| 半自动分发 | API 受限或社区规则严格的平台 | 系统生成文案与配图，运营一键复制/定时提醒发布 |
| 定时任务 | 全部平台 | 错峰发布，避免被判定为垃圾营销 |

**必须说明的前提**：各平台对自动发布有账号资质、应用审核与频率限制；Reddit 等社区对自我推广有严格规则。方案以"合规优先"，不承诺绕过平台限制，也不做群发、刷量或批量私信。

**发布节奏（建议）**：LinkedIn 每周 2–3 条；Reddit 每周 1–2 条（技术答疑为主）；X / Facebook 按需；全部进统一内容日历，避免同一时间刷屏。

### 5.3 短视频（YouTube）与站内反哺

**内容方向**：首批聚焦 **30–50 个核心热销型号**，每个 1–3 分钟——产品实拍与封装细节、同系列对比、选型避坑、库存/交期说明。

**YouTube SEO**：标题采用"型号 + 关键参数 + 应用场景"长尾结构；描述区放型号、参数、带 UTM 的站点链接；章节、字幕、封面统一规范；视频页输出 VideoObject 结构化数据。

**站内反哺**：视频嵌入对应详情页，提升停留与内容厚度；看完视频可在同页直接询价；视频下方展示相关型号与资料下载，形成闭环。

### 5.4 外链三层策略

> 外链不是买排名，而是把 Ds Bit 产出的技术数据，变成行业愿意主动引用的内容。

**三条红线（明确不做）**：不购买链接、不做链接农场（PBN）；不批量注册论坛发签名、不群发私信；不为了数量进"交钱就收录"的低质目录。

**一条标准**：所有外链动作必须满足**可被编辑性引用**——对方是因为内容有用而主动链过来，而不是交易来的。

#### 第一层：基础信任层（可立即启动，无前置依赖）

| 渠道类型 | 具体平台（示例） | 做法 |
|---|---|---|
| 电子元器件垂直 B2B | Europages（基础版免费）、EC21、Global Sources | 提交企业资料、主营品类、核心型号页链接 |
| 行业协会 / 媒体目录 | "electronic components association member directory" 类目录 | 申请加入供应商列表，有审核门槛的优先 |
| 站内坏链修复 | 现有页面中的失效外链、失效资料引用 | 盘点并替换为可用来源 |

原则：**不追求数量。** 10 个有审核、有真实流量的目录，价值高于 500 个垃圾目录。

交付物：已提交目录清单、审核状态记录、企业资料标准包（中英文简介、资质、主营品类、Logo）。

#### 第二层：技术引用层（跟在 Ds Bit 首批参数页之后）

这是本项目区别于普通 SEO 外包的核心——外链的"落脚点"不是首页，而是参数对比页。

- **动作一：替代料 / 选型对比页（自动生成）**。利用 Ds Bit 对同品类多个型号的解析结果，生成"X vs Y 参数对比""某型号的可靠替代方案"类页面。这类页面天然具备被论坛、博客、采购指南引用的价值，也能批量覆盖长尾型号。
- **动作二：工程师社区技术参与（非广告）**。在 EEVblog、Engineering.com、r/AskElectronics、r/PrintedCircuitBoard 等社区，以技术讨论身份回答"某型号能否替代""某参数如何理解""封装差异在哪"，在确有帮助时引用对应参数对比页。
- **动作三：失效链接修复（Broken Link Building）**。找出元器件领域已被引用但已失效的资料页，联系引用方，提供 morrishk 对应的可用页面作为替代。

**前提必须说清楚**：Reddit 等社区对自我推广容忍度极低。只有"有数据出处的技术回答"才被接受；纯链接、软文、批量账号会被封禁，也会反噬品牌。因此这一层按"技术贡献"而非"推广"来管理。

**前置条件**：这一层的效果完全取决于参数页质量，必须先有 Ds Bit 灰度产出的高质量结构化参数才能启动。

#### 第三层：技术权威层（长期资产，交付后持续）

GitHub 是电子与技术类 B2B 被严重低估的外链来源：域名权重高、抓取快，而且 AI 搜索（ChatGPT、Perplexity 等）在回答技术问题时高频引用 GitHub 内容。

- 将 Ds Bit 的参数提取规则、数据字典、选型字段规范（**脱敏后，不含客户数据与商业信息**）以开源工具或技术文档形式发布。
- 向 awesome-electronics、awesome-hardware 等 Awesome 列表提交 PR。
- 收益不止外链：当工程师问 AI"如何批量提取元器件 Datasheet 参数"时，这份文档可能成为引用来源——也就是常说的 GEO（生成式引擎优化）。

### 5.5 UTM 与归因（引流的前提是能算账）

| 能力 | 做法 | 结果 |
|---|---|---|
| UTM 标准化 | 所有社媒/视频/外链自动植入来源、媒介、活动 | 能区分 LinkedIn 帖子、Reddit 讨论、YouTube 视频、目录站 |
| 站内事件 | 浏览、搜索、查看参数、点击询价、提交表单 | 能看到用户路径与断点 |
| 服务端回传 | 表单提交通过 Measurement Protocol 回传 GA4 | 即使浏览器装了拦截插件，询盘仍可归因 |
| 归因报表 | 渠道 → 落地页 → 询盘 | 知道该加码哪个平台、停掉哪个平台 |

**合规**：面向欧盟流量时，按当地要求配置 Cookie 同意后再加载分析工具。

### 5.6 节奏与阶段目标

| 时间 | 目标 | 衡量方式 |
|---|---|---|
| 第 1 个月 | 打通分发链路；完成首批 10 条内容与 5 条视频；完成第一层目录提交 | 内容日历、发布记录、目录审核状态 |
| 第 3 个月 | 社媒稳定输出；视频覆盖 20–30 个核心型号；外链第一层基本完成 | 渠道会话数、站内停留、渠道询盘数 |
| 第 6 个月 | 形成"社媒/视频/外链 → 站内 → 询盘"的稳定归因 | GA4 归因报表、询盘来源占比 |

> 具体增长目标需结合客户内容产能与账号基础，在启动会后设定。

## 六、P0-3：询盘转化

> 前两章解决"人来了"，这一章解决"人走了没"。**询盘链路是第一阶段唯一直接产生收入的部分，必须当成产品来设计。**

### 6.1 现状问题

| 问题 | 具体表现 | 后果 |
|---|---|---|
| 入口分散 | 详情页表单、购物车、邮件三条路并存 | 客户不知道走哪条，销售收到的东西格式不一 |
| 字段偏多 | 沿袭早期表单设计 | 移动端放弃率高，尤其工程师在车间/展会场景 |
| 无多型号能力 | 一个型号一次提交 | 采购要问 20 个料号，只能发邮件 |
| BOM 无入口 | 只能邮件往返 | 大单响应慢，且需求不进系统 |
| 无回执 | 提交后只有邮件 | 客户不确定是否收到，容易重复提交或流失 |
| 无有效询盘判定 | 数量与质量混在一起 | 无法判断渠道与产品页的真实效果 |

### 6.2 三条询盘路径

| 路径 | 适用场景 | 客户动作 | 系统动作 |
|---|---|---|---|
| **A 单型号询价** | 已确定型号，只要价格/交期 | 填数量 + 需求，点提交 | 生成线索 → 邮件通知销售 → 页面回执 + 邮件回执 |
| **B 多型号批量询价** | 一次问 5–50 个料号 | 加入询价清单 → 统一提交 | 生成一条线索 + 多个明细行 → 汇总邮件 |
| **C BOM 上传** | 整单采购、有 Excel/CSV/PDF | 上传文件 + 填联系方式 | 存原件 → 记录型号数（人工或后续解析）→ 转销售 |

**关键设计：BOM 上传在第一阶段只做"收得下、存得住、追得到"，不做自动分析。**

- 客户上传的文件原样保存，不承诺自动识别与报价；
- 系统只做基础校验（格式、大小、是否为空），并记录"该询盘含 BOM 文件"；
- 销售侧拿到的是**完整原始文件 + 客户需求描述**，由人工跟进；
- 后续如需自动匹配，属于 P2 模块，接口预留即可（见 10.2）。

### 6.3 表单设计原则

1. **必填最少**：邮箱 + 数量 + 型号（自动带入）即可提交；公司、电话、国家为选填。
2. **型号自动带入**：从详情页进来时型号已填好，客户不用重复输入。
3. **数量可留空**：允许"待定"，不因为一个字段卡住询盘。
4. **移动端优先**：单列表单、大按钮、数字键盘、支持拍照上传 BOM。
5. **即时回执**：提交后页面明确显示"已收到，X 小时内回复"，并同步发邮件。
6. **反垃圾**：图形/行为校验 + 频率限制，不用会让真实客户放弃的复杂验证码。

### 6.4 线索落地与销售跟进

| 环节 | 设计 |
|---|---|
| 存储 | 统一线索库（线索主表 + 明细行 + 附件），不再只依赖邮件 |
| 通知 | 邮件 + IM 通知销售；高价值线索（含 BOM / 数量大）单独标记 |
| 状态 | 新建 → 已联系 → 报价中 → 成交 / 无效（用于统计有效询盘） |
| 回执 | 客户侧自动回执邮件，含询盘编号与提交内容摘要 |
| 导出 | 支持按时间、渠道、产品导出，供销售复盘 |
| 时效 | 目标：工作时间内 4 小时首次响应（口径待与销售侧确认） |

### 6.5 统计口径（与第十二章一致）

```
产品页访问量 → 点击询价 → 提交询盘 → 有效询盘（销售判定） → 成交
```

每一步都要能按**渠道 / 产品 / 语种**拆分。这是判断"该继续投哪里"的唯一依据。

### 6.6 交付标准

- 三条询盘路径全部可用，移动端可完成全流程。
- 线索进入统一线索库，可按渠道与产品统计。
- 客户提交后 1 分钟内收到回执邮件。
- GA4 可看到"提交询盘"事件，且带 UTM 归因。
- 有效询盘可由销售标记，报表可出"询盘数 / 有效询盘数 / 有效率"。

## 七、P1-1：站内搜索（Meilisearch）

**目标**：工程师怎么输入都能找到；找不到时给建议，而不是把人赶走。

| 能力 | 现状 | 升级后 |
|---|---|---|
| 拼写容错 | 错一个字符就失败 | 自动纠正/近似匹配 |
| 中缀匹配 | 只认开头 | 输入型号任意片段都能命中 |
| 空格/符号 | 直接失败 | 自动归一化 |
| 响应速度 | 依赖数据库前缀扫描 | 毫秒级 |
| 筛选 | 无 | 品牌、分类、封装、库存、是否有资料 |
| 排序 | 固定 | 相关性、库存、型号、价格 |
| 无结果 | 跳转询价车 | 保留在搜索页，给相近型号、分类入口和询价按钮 |

**工程原则**：

- 数据是静态终态，**不做复杂的实时同步**，采用一次性全量建索引 + 版本化切换。
- 精确完整型号仍走数据库唯一索引，保证"输入完整料号"零延迟、强一致。
- 检索引擎故障时自动回退旧查询，页面不报错。

## 八、P1-2：SEO 与多语种

### 8.1 结构化数据：让谷歌"看懂"产品页

| 页面 | 输出内容 | 作用 |
|---|---|---|
| 首页 | 公司信息、站点搜索入口 | 品牌实体识别 |
| 分类/品牌 | 面包屑、商品列表 | 层级理解 |
| 详情页 | 产品名、品牌、型号、参数、库存/价格（或询价） | 产品富结果 |
| 文章 | 文章结构、作者、发布时间 | 内容理解 |
| 含视频页 | 视频对象标记 | 视频搜索曝光 |

**原则**：询价商品不虚构价格；停产商品明确标注；参数只输出已审核数据。

### 8.2 URL 与抓取

- 老 URL 全部保留；只对协议、主机名、大小写做规范化跳转。
- 每个页面输出自指 canonical。
- 五语种互相声明 hreflang，默认指向英文。
- 千万级页面按"在售、全量、长尾"分层生成 sitemap，分片提交。
- 不存在的产品返回真正的 404，不再返回"200 + 错误文字"。

### 8.3 五语种

| 语种 | 策略 |
|---|---|
| 英文 | 主站，默认语言 |
| 德/日/西/印尼 | 复用现有完整词库，补新增词条 |
| 其余 75 个域名 | 先盘点流量，保留可访问，不盲目投入翻译 |

**翻译边界**：只翻译"人写的说明性内容"（界面、分类名、参数名、文章）；**型号、品牌、封装等事实数据绝不翻译**——这是元器件行业的通行做法，也是 SEO 的正确做法。

## 九、P1-3：Ds Bit 参数化（服务于详情页）

### 9.1 正确定位

Ds Bit 仍然重要，但**它服务于详情页，而不是一个独立的技术目标**。判断它做得好不好，不看解析了多少 PDF，而看**重点产品页的参数是否完整、是否可信、是否带来了更多长尾搜索与询盘**。

### 9.2 链路

```
PDF Datasheet
     ↓
Ds Bit 离线解析
     ↓
参数标准化 + 质量审核
     ↓
morrishk 产品参数库
     ↓
产品详情页展示
     ↓
SEO 收录 + 社媒分享
     ↓
客户询盘
```

### 9.3 覆盖策略：不追求全量，先打重点

前期不需要让每个产品都有完整参数。优先覆盖**高流量、高价值、有 PDF、有询盘潜力**的产品：

| 批次 | 范围 | 目的 |
|---|---|---|
| B0 | **100–200 份文档**（覆盖 5 种 DocType） | 算法与质量门校准 |
| B1 | **1–2 万份文档**（高价值型号） | 验证成本与准确率，直接支撑详情页上线 |
| B2 | 按分类扩展 | 覆盖主要目录 |
| B3 | 长尾 | 视预算与收益再决定 |

> **计量单位口径（P0-04 修订）**：上表的 B0 / B1 一律按**文档份数（Document）**计，不按产品型号数计。一个型号可能关联多份 PDF，一份 PDF 也可能被多个型号共享，两者不可互换。
>
> 「3–5 万个重点型号」是**详情页覆盖目标**，不是 PDF 解析量；对应的解析工作量按 1–2 万份文档估算。
>
> B1 扩量须同时满足：B0 质量门通过、关联审核完成、单份成本复核通过。技术版 7.2 与本表口径一致。

**判断标准**：B1 完成后，若"重点产品页的参数覆盖率"与"这些页面的询盘转化"出现正向变化，再决定是否扩量——**用数据决定投入，而不是一次性铺开 56.9 万个 PDF。**

### 9.4 质量与灰度

- **质量门**：参数行数、置信度、关键参数、单位合法性、数值范围、与现有字段冲突检测。
- **人工抽检**：每批 ≥ 500 件，准确率 ≥ 95% 才发布。
- **灰度**：按分类白名单 → 10% → 50% → 100%，每级观察 72 小时。
- **可撤下**：关闭开关即回退到原有字段，结构化数据同步撤下。
- **错误闭环**：用户报错 → 定位到 PDF 页码 → 单条回滚 → 重解析。

## 十、P2：后续可选模块（不阻塞前期上线）

> 这一章的内容**不在第一阶段交付范围**，列出来是为了说明：方案已经为它们预留了位置，但不会因为它们而拖慢获客。

### 10.1 BOM 智能匹配为什么后置

老板已经明确反馈 BOM 细节复杂，那么就不应该在第一阶段投入大量资源建设完整 BOM 系统。BOM 涉及的复杂问题包括：

| # | 复杂点 | 为什么难 |
|---|---|---|
| 1 | 多行物料清单导入与字段识别 | 客户 BOM 格式千差万别，列名、单位、合并单元格都不统一 |
| 2 | 制造商、型号、封装、数量等字段标准化 | 同一颗料有多个写法、多个别名 |
| 3 | 停产、替代、兼容型号识别 | 需要工程判断，不是字符串匹配 |
| 4 | 库存、价格、交期的实时性 | 站内数据是静态终态，实时性需要上游系统对接 |
| 5 | 多个替代型号之间的优先级 | 取决于客户采购条件与工程约束，不是单一排序 |
| 6 | 客户采购条件与工程约束 | 商业规则，需人工参与 |

这些问题不仅是技术问题，还涉及**供应链数据、工程判断和商业规则**。在数据与规则都不具备的情况下强行自动化，产出的是"看起来很像、但不能用"的结果，反而伤害专业形象。

### 10.2 前期的最小替代方案

**客户上传 BOM 或填写多个型号 → 网站记录需求 → 销售人工跟进。**

- 不承诺自动 BOM 分析；
- 不承诺自动替代料推荐；
- 不承诺自动报价。

这样既保留了未来扩展空间（线索与附件都已结构化存储），也不影响当前获客目标。

### 10.3 Cross Reference（替代料对照）

- 在第一阶段只做**静态展示**：详情页的"相关型号"里列出同封装/同系列的候选，并标注"需工程师确认"。
- 真正的 IC 级平替（并列关键电气参数差异、按差异度排序）属于 P2，依赖参数库覆盖度达到一定水平。

### 10.4 AI Agent 工作台

> 这一块解决的不是"让谷歌搜到"，而是"让工程师留下来、让大客户离不开"。但它必须有客户才有意义。

**能力轮廓（P2）**：

| 能力 | 说明 |
|---|---|
| 智能参数问答 | 自然语言问"3.3V 供电、SOT-23 封装的低功耗 LDO"，系统拆成参数条件检索 |
| 物理溯源 | 每条参数可定位到原厂 PDF 的某一页、某张表、某一行，并画出红框 |
| BOM 配单 | 上传 Excel/CSV，逐行匹配站内型号、封装与库存，生成整单参考 |
| 大客户私域门户 | 挂载企业内规、历史测试报告、专属报价单（**需客户授权并提供数据**） |
| 运营自动化中枢 | 上新、内容、分发、配单由引擎接走重复劳动 |

**底座说明**：Agent 的参数事实来自 Ds Bit 的结构化结果，大模型只负责理解提问与组织输出，不负责"编参数"；查不到就明确说"数据中没有"，不用相似型号顶替。

**边界**：替代料结论一律标注"工程候选建议"，最终放行需客户工程师完成台架验证；库存、价格、交期沿用站内数据并标注截止日期。

### 10.5 什么条件下启动 P2

| 触发条件（建议） | 说明 |
|---|---|
| 月询盘量达到稳定水平 | 说明获客链路已跑通，值得投入提升客单价与黏性 |
| 重点产品参数覆盖率达到目标 | Agent 与 BOM 匹配的准确性依赖参数库 |
| 销售侧确认"BOM 询盘占比高、人工处理吃力" | 用真实痛点驱动，而不是技术想象 |
| 客户愿意提供私域数据与授权 | 否则 KA 门户无法落地 |

> 满足上述条件后，再单独立项评估，不影响第一阶段节奏。

## 十一、实施路径与节奏

### 11.1 阶段划分

| 阶段 | 周期（参考） | 主要内容 | 验收标志 |
|---|---|---|---|
| **底座（并行）** | 约 2–3 周 | 稳定性加固、日志与告警、备份演练、安全加固、URL 基线 | 连续稳定运行；老 URL 抽样全部可访问 |
| **P0 第一阶段** | 约 6–8 周 | 详情页重构、询盘三路径与线索库、社媒/视频/外链启动、UTM 与归因 | 详情页可承接；询盘可提交可统计；站外开始有带 UTM 的流量 |
| **P1 第二阶段** | 约 6–8 周 | 新搜索、Ds Bit 参数化（B1 批次）、结构化数据、sitemap、五语种 | 搜索容错达标；参数抽检达标；富结果无错误 |
| **P2 后续（可选）** | 另行评估 | BOM 智能匹配、Cross Reference、Agent 工作台、运营中枢 | 依 10.5 的触发条件立项 |

> 周期为方向性参考，详细任务拆解、人力配置与排期在项目启动会后提供。P0 内部的三件事可并行，但**详情页必须先于参数化全量上线**——否则参数没有地方展示。

### 11.2 关键路径

```
底座加固 ──┬─→ 详情页重构 ──→ 询盘三路径 ──→ 归因与报表
           │                        ↑
           └─→ 社媒/视频/外链 ──────┘（带 UTM 落地）

详情页 ──→ 参数化 B1 ──→ 结构化数据 ──→ 外链第二层（对比页）
                     └─→ sitemap / 五语种
```

### 11.3 一次只动一个变量

不同时改 URL、换模板、切搜索、开参数。每项变更独立灰度、独立观察、独立回滚。

### 11.4 成本口径（不含报价）

本项目的主要变动成本来自四块，提前说明，便于客户判断范围：

1. **PDF 解析算力**：56.9 万个 PDF 是最大变量。建议按"重点型号优先"分三批推进，首批 1–2 万份文档，用真实数据校准单份成本后，再决定全量范围。
2. **检索与存储资源**：千万级索引需要独立实例；PDF 与图片建议使用对象存储 + CDN，不占应用服务器磁盘。
3. **翻译与内容**：现有五个语种只补新增词条，不新增语种。
4. **内容生产（社媒与视频）**：视频拍摄与文案是 P0 的持续投入项，取决于自制还是外包。

> 具体报价与商务条款由商务侧另行提供，本文不涉及价格。

## 十二、验收指标

> 不能只用页面数量、解析 PDF 数量、外链数量来衡量项目成功。**第一阶段按下面这组指标验收。**

### 12.1 指标体系

| 指标 | 定义 | 关注点 | 责任环节 |
|---|---|---|---|
| **产品页访问量** | 详情页 UV / PV，按渠道拆分 | 是否获得更多有效流量 | P0-1 / P0-2 |
| **询盘转化率** | 提交询盘数 ÷ 产品页访问量 | 访问产品页后有多少人提交询盘 | P0-1 / P0-3 |
| **有效询盘数** | 销售判定为真实采购需求的询盘数 | 是否带来真实采购需求 | P0-3 |
| **渠道贡献** | SEO / LinkedIn / Reddit / YouTube / 外链 各自带来的询盘数 | 该加码或停投哪个渠道 | P0-2 |
| **产品参数覆盖率** | 重点产品页中有完整参数表的比例 | 重点页是否具备有用的技术信息 | P1-3 |
| **询盘响应情况** | 首次响应时长、跟进率 | 询盘是否及时进入销售流程 | P0-3 |

### 12.2 基线建立（启动后第 1–2 周完成）

- 现状产品页访问量、询盘提交数、有效询盘数（按现有口径回溯 3 个月）。
- 现有表单的字段级放弃率（从 GA4 事件与日志推算）。
- 现有渠道占比（自然搜索 / 直接 / 引荐 / 社媒）。
- 重点产品清单（按流量与询盘潜力排序）。

**没有基线的指标不算指标。** 这一步做完，后续所有承诺才有参照物。

### 12.3 明确不采用的验收方式

| 不采用 | 原因 |
|---|---|
| 交付页面数量 | 页面多不等于有效 |
| 解析 PDF 数量 | 解析量大不等于页面有用 |
| 外链条数 | 数量可以刷，质量不能 |
| 首页/列表页 UV 总量 | 与询盘相关性弱，容易被无关流量稀释 |

## 十三、风险控制与回滚预案

### 13.1 风险矩阵

| 风险 | 可能性 | 影响 | 应对 | 回滚条件 |
|---|---|---|---|---|
| 改 URL 导致排名下滑 | 中 | 极高 | URL 冻结；只做规范化跳转；上线前万级抽样 | 收录量明显下滑 |

### 13.2 URL 兼容性控制

- 把现有 URL 规则列为"不可变更基线"。
- 新增路径必须避开现有兜底规则，且有自动化测试。
- 上线前从访问日志抽取一万条老 URL 做回归：状态码、标题、主标题、canonical 全部校验。
- 上线后四周内每日抽样，错误率超阈值立即回滚。

### 13.3 数据迁移控制

- 千万行主表**本期不动**；新增数据放新表。
- 新缓存表构建完成后原子换名，秒级切换。
- 任何结构变更前必须有可恢复快照，并在测试环境演练。
- 切换后校验行数、抽样字段、核心页面与查询性能。

### 13.4 回滚方式

| 变更 | 回滚方式 | 目标 |
|---|---|---|
| 搜索切新引擎 | 关闭开关，回旧查询 | 分钟级 |
| 索引版本问题 | 别名指回旧版本 | 分钟级 |
| 参数表上线 | 关闭开关，回原字段 | 分钟级 |
| 新缓存表 | 反向换名 | 分钟级 |
| 新界面 | 回滚视图模板 | 十分钟级 |
| 新询盘表单 | 切回旧表单入口 | 分钟级 |

### 13.5 数据时效声明

数据截止 2024-11-30，属于静态终态。全站将明确标注：

- "Data last updated: 2024-11-30"
- 库存与价格"仅供参考，下单前请确认"
- 询价成功页与邮件同步声明

这不是免责，而是让客户和买家都建立在准确预期上。

### 13.6 上线前检查（Go / No-Go）

- 连续稳定运行，无 5xx 尖峰。
- 日志轮转、磁盘告警、备份恢复演练全部通过。
- 万级老 URL 回归通过。
- 询盘三条路径端到端可用，回执正常。
- 搜索典型用例全部达标，降级演练通过。
- 参数抽检达标，结构化数据无错误。
- 多语种互指正确，sitemap 可抓取。
- 回滚演练完成，耗时符合预期。
