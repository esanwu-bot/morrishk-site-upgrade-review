## 1. 记录规则

1. 只有**书面**裁定才进入本表；会议口头同意、聊天记录中的「可以」、执行 Agent 的建议，均不视为裁定。
2. 每条裁定必须写明：问题编号、决定、决策人、日期、证据基线、前提/假设、影响范围、生效条件。
3. 裁定不得绕过主文档 §14.2 的审批边界。
4. 裁定不得把 `OPEN` 直接改写为 `CLOSED`；本表只记录「已裁定」，原始 Open Questions 的状态更新由授权维护人另行处理。
5. 若裁定改变选项或引入新前提，必须同时登记「推翻了哪条既有假定」，不得静默覆盖。
6. 执行 Agent 不得代填「决策人」「结论」「日期」三列。

### 2.1 IQ-01 裁定全文（转录）

| 项 | 内容 |
|---|---|
| 决定 | 正式废弃 `doc-id` 作为跨系统产品主键的设计。 |
| 决定 | `prod-{document_id}` 仅作为文档处理、解析和流转的内部临时凭证；**不得**作为：Morrishk 产品主键、跨系统产品业务键、永久产品身份、产品分类映射键。 |
| 决定 | 正式采用 **MPN + Brand** 作为统一跨系统产品业务身份。 |
| 决定 | 所有产品在进入跨系统身份处理前，必须通过统一、版本化的 `MpnNormalizer`。 |
| 决定 | `MpnNormalizer` 必须定义并版本化：首尾与内部空白、大小写、连接符、Unicode 归一、空值/非法值/冲突处理、原始 MPN 保留。 |
| 决定 | 禁止在不同模块中各自实现 MPN 清洗逻辑。 |
| 决定 | 唯一键为 `(mpn_norm, brand_norm)`；即使当前数据中一个 MPN 只出现一个 Brand，也不得临时改变该结构。 |
| 决定 | 必须保留字段：`mpn_raw`、`mpn_norm`、`brand_raw`、`brand_norm`、`normalizer_version`、`product_business_key`。 |
| 决定 | `product_business_key` 必须确定性生成；须文档化编码、字段分隔、空值处理、哈希算法；**不得**只使用未经碰撞分析的截断哈希作为唯一身份。 |
| 决定 | 同一 `mpn_norm` 对应多个 `brand_norm` → 多个独立产品业务身份。 |
| 决定 | 同一 `(mpn_norm, brand_norm)` 对应多个来源文档 → 文档可关联同一产品业务身份，但不得因此生成多个产品身份。 |
| 决定 | 缺少 Brand、Brand 无法确认或规范化结果冲突 → 进入待确认状态，不得自行合并产品。 |
| 推翻的既有假定 | 原 IQ-01 建议 A（Ds Bit 全局注册表 + ULID `product_id`）、原主文档 §6.2 的 `product_id` 代理键模型、原 §9.4.2 `dsbit_product_id` 映射主键。 |
| 不在裁定内 | `product_business_key` 的具体哈希算法/编码格式、`MpnNormalizer` 规则细节、`identity_scope` 是否进入业务键 —— 均仍为设计待定项，须在实现前以设计文档固定并评审，不得由执行 Agent 自行当作已批准。 |

### 2.2 IQ-02 裁定全文（转录）

| 项 | 内容 |
|---|---|
| 决定 | 严格分离两套分类体系。 |
| 决定 | **业务导航分类**：旧站 `snsii_product_category`、新平台 `pd_category`，仅用于前台展示、导航与目录组织；**不得**直接作为 Ds Bit 技术参数分类；**不得**将两套系统分类 ID 直接共享。 |
| 决定 | **技术参数分类**：由 Ds Bit 引擎管理与生成；PM 提供首个真实分类种子与参数命名标准。 |
| 决定 | 候选核心字段至少包括 `Package`、`Voltage`、`Operating_Temperature`；正式 code、定义、单位、数据类型、适用范围、别名以 PM 确认的种子为准，**不得由执行 Agent 自行臆定**。 |
| 决定 | 参数字典建议字段：`parameter_code`、`canonical_name`、`display_name`、`definition`、`data_type`、`canonical_unit`、`applicable_scope`、`synonyms`、`source`、`dictionary_version`、`status`。 |
| 决定 | **Fixture 边界**：开发 Fixture 仅用于 UI 与 Mock 展示，必须显式标记 `DEMO_FIXTURE`；不得作为正式种子、不得混入正式字典、不得把 Fixture ID/定义写入正式业务数据、不得把 Fixture 测试通过描述为真实数据验证；UI 使用隔离 Demo Fixture 时必须显示演示数据标识。 |
| 推翻的既有假定 | 原 IQ-02 建议「v1 只允许一个 PUBLISHED 体系、种子由客户业务团队提供」未被推翻；本轮进一步把「技术参数分类」与「业务导航分类」的职责边界写成硬约束，并明确 PM 种子责任。 |
| 不在裁定内 | 体系数量（单/多 taxonomy）、`category_code` 生成规则（IQ-03）、多主分类（IQ-04）、生命周期/410（IQ-05）仍为 `OPEN`。 |
