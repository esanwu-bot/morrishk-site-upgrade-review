## IQ-05 分类合并/停用保留期与 410 时机

### 问题

分类被停用、合并或拆分后，API 对外还应保留多久的可读窗口？`410 CATEGORY_RETIRED` 在何时生效？
保留期内旧分类页、旧映射是否仍可用？生命周期字段由哪个系统承载？

### 现状证据（可复核）

| 证据 | 位置 | 结论 |
|---|---|---|
| 旧站分类表无生命周期字段 | `01_schema.sql:347-363`（经 `PHASE0_OPEN_QUESTIONS_MATRIX.md` IQ-05 引用） | 无 `status` / `deprecated_at` / `deleted_at`；删除即不可用 |
| 现有系统无 410 语义 | 旧站源码与路由 | 未发现任何 `410` 处理或分类退役概念 |
| 设计建议保留期 | 主设计 §7.5.6；§7.2.4 | 建议 180 天，明确标注 `OPEN`（IQ-05） |
| 候选语义 | 主设计 §7.5.6 / §8.3 | 保留期内 `200 + status=DEPRECATED`；期满 `410 CATEGORY_RETIRED`；历史边与 tombstone 保留 |

### 选项

| 选项 | 内容 | 优点 | 风险 |
|---|---|---|---|
| A | 保留期 180 天，自 `deprecated_at` 起算 | 与设计建议一致；给迁移留出窗口 | 需要业务确认 180 天足够 |
| B | 保留期 365 天 | 对长尾 SEO 与历史映射更安全 | 长期维持 DEPRECATED 数据与页面 |
| C | 永久可读（不进入 410） | 兼容性最好 | 分类树无限膨胀；与“退役”语义冲突 |
| D | 其他（自定义窗口 / 分级窗口） | 可按分类层级或流量区分 | 规则复杂，测试矩阵扩大 |

### 影响

- `GET /categories/{category_id}` 的 `200` / `410` 边界。
- Morrishk 本地映射 `STALE` 保留策略、旧分类页下线时机、301 计划（IQ-18）。
- 契约候选 §6.4 / §9.4 的消费方行为；`degraded_allowed=true` 的持续时间。
- 新表需承载 `status` / `deprecated_at` / `merged_into` / `split_into` / tombstone（与 IQ-15 耦合）。

### 分析建议（非裁定）

建议 A（180 天），并把 `deprecated_at` 起点固定为“分类最后一次发布状态变更时间”，
保留期内允许读取但不允许新建产品归属。理由：与现有设计一致，窗口足以覆盖一次完整同步与人工迁移；
365 天与永久方案需要额外运维成本与清理机制。

### 决策人与生效条件

- 决策人：客户业务负责人 + Reviewer（见矩阵）。
- 生效条件：书面裁定登记 + 独立 Reviewer 验收；新表生命周期字段落地方案随 IQ-15 一并确认。

## IQ-09 错误响应包最终形状

### 问题

Business API 的错误响应采用哪种外层形状：
现有平台统一包 `{code, message, data, request_id, meta}`、任务书建议的 `{"error": {...}}`、还是双写？

### 现状证据（可复核）

| 证据 | 位置 | 结论 |
|---|---|---|
| 现有平台契约包 | `platform/docs/phase1/03-api-contract.yaml:9-14`（矩阵引用 9-12） | 定义 `{code, message, data, request_id, meta}`，`code=0` 成功 |
| 前端错误解析 | `platform/web/src/lib/api/client.ts:28-36,77-90` | `ApiError` 已按 `code` / `message` / `request_id` 解析 |
| Ds Bit 静态桩 | `workbench/b2b/serve_b2b.py:240-265` | 返回自定义结构；未跟踪文件，不构成契约 |
| 设计建议 | 主设计 §5.7 / 附录 B | 采用现有包；把任务书 `error` 字段映射进 `meta` |

### 选项

| 选项 | 内容 | 优点 | 风险 |
|---|---|---|---|
| A | 现有包 `{code, message, data, request_id, meta}` | 同组织内形状统一；前端已有解析 | 与任务书建议字面不同，需书面说明映射 |
| B | 任务书 `{"error": {"code": "...", ...}}` | 与任务书字面一致 | 与现有平台出现两套形状；前端需改 |
| C | 双写：同时返回 `error` 与 `meta` | 过渡期兼容 | 响应冗余；长期维护两套语义 |

### 影响

- 全部端点的成功/失败包；所有客户端与契约测试断言。
- 错误码、`retryable`、`degraded_allowed` 语义在三种选项下不变，只改变外层字段位置。
- 与 IQ-21 无关，可独立先裁。

### 分析建议（非裁定）

建议 A，并在附录 B 保留到任务书 `error` 对象的字段映射说明。
理由：现有平台与前端已有实现，避免同一组织两套错误形状；错误语义四维度（HTTP、`code`、`error_key`、重试/降级）保持不变。

### 决策人与生效条件

- 决策人：Reviewer + Ds Bit 负责人。
- 生效条件：书面裁定登记；契约候选 §7.3 与 OpenAPI 更新前不得宣称定稿。

## IQ-15 新表引擎与字符集

### 问题

新增的 Ds Bit 侧或同步侧数据表应使用 InnoDB + `utf8mb4`、MyISAM + `utf8`，还是独立数据库？
是否与旧表同库？

### 现状证据（可复核）

| 证据 | 位置 | 结论 |
|---|---|---|
| 旧站表引擎盘点 | `mysql_schema_audit/02_table_inventory.csv`（经矩阵引用） | 31 张表：30 张 MyISAM、1 张 InnoDB |
| 旧站字符集 | `01_schema.sql` 各表 `ENGINE=` / `CHARSET=` 行 | 全部 `utf8`（非 `utf8mb4`） |
| 运行环境 | 旧站源码快照 | PHP 7.4.33 / MySQL 5.6.50 |
| 新平台迁移头 | `platform/db/migrations/20261116_0002__pd_model_core.up.sql:8` | 要求 MySQL 8，明确禁止 production |

### 选项

| 选项 | 内容 | 优点 | 风险 |
|---|---|---|---|
| A | InnoDB + `utf8mb4` | 事务、崩溃恢复、完整 Unicode；与 MySQL 8 迁移方向一致 | 与旧库 5.6 / MyISAM 运维习惯不同；需确认实例版本 |
| B | MyISAM + `utf8` | 与旧表一致，迁移摩擦小 | 无事务/外键；不能存储完整 Unicode（emoji、部分符号） |
| C | 独立数据库（InnoDB + `utf8mb4`） | 隔离风险；便于独立备份与权限 | 需要新实例/新库运维与网络配置；跨库查询不可用 |

### 影响

- 全部新表 DDL、索引、备份、恢复与性能基线。
- `product_business_key` 为纯 ASCII，本身不受字符集影响；但 `brand_raw` / 分类名 / 别名需要 `utf8mb4`。
- 事务边界与并发控制；`data_version` 单调递增的实现方式。
- **不改变 API 线形**，因此可在契约冻结后、实现前裁定。

### 分析建议（非裁定）

建议 A（InnoDB + `utf8mb4`），若生产实例版本或运维隔离要求不允许，则退到 C（独立库）。
不建议 B：无事务与外键会与“边不物理删除 + `valid_to` + `superseded_by_edge_id`”的一致性要求冲突，
且 `utf8` 无法完整承载品牌与分类多语言字符。

### 决策人与生效条件

- 决策人：运维 + Morrishk 技术负责人。
- 生效条件：书面裁定 + 实例版本/容量核验；DDL 评审通过前不得建表。

## IQ-21 是否允许非生产凭证

### 问题

Phase 1/2 本地联调是否允许创建“非生产”OAuth2 凭证（本地/预发）？还是只能使用静态桩？

### 现状证据（可复核）

| 证据 | 位置 | 结论 |
|---|---|---|
| 无 OAuth2 实现 | Ds Bit 仓库检索（经矩阵引用） | 未发现 Token 签发、客户端注册或 scope 校验实现 |
| 静态桩 | `workbench/b2b/serve_b2b.py:34-37,189-224` | `/oauth/token` 返回固定标记且不校验凭据；未跟踪文件 |
| 生产凭证边界 | 本轮任务书 | 生产凭证明确禁止在本设计范围内创建 |

### 选项

| 选项 | 内容 | 优点 | 风险 |
|---|---|---|---|
| A | 允许本地/预发非生产凭证，严格隔离 | 可验证真实 Token 刷新/过期/撤销传播 | 需要签发、存储、轮换、清理规则；误指向生产数据的风险 |
| B | 只允许静态桩，不签发任何凭证 | 最保守；零凭证泄露面 | 无法验证真实 Token 流程与 60 秒撤销语义 |
| C | 只允许预发凭证，不允许本地 | 折中；更接近生产 | 本地开发仍需桩；预发环境需先具备 |

### 影响

- Phase 1/2 联调方案与安全审计范围。
- 若选 A：必须满足非生产域名、非生产数据、secret 不入 Git、测试结束即撤销、不得写入任何文档或提交历史。
- 若选 B：契约测试只能验证桩行为，不能声称 Token 流程已验证。
- 与 IQ-11（客户端注册与轮换责任人）、IQ-10（域名拓扑）相关。

### 分析建议（非裁定）

建议 A，但附加硬约束：非生产域名 + 非生产数据 + secret 不落盘/不入 Git + 测试结束即撤销；
且所有凭证不得写入本仓库任何文件。若安全负责人要求更保守，C 是可接受的退让。

### 决策人与生效条件

- 决策人：客户业务负责人 + 安全。
- 生效条件：书面裁定 + 凭证管理规则登记；在裁定前不得签发任何凭证。
