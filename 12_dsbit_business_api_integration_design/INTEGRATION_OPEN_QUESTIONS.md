## IQ-01 产品身份权威与 ID 空间（MPN / `product_id` / 旧站 ID / `pd_model.id`）

**问题**

一个"产品"在系统间用什么作为权威身份？Ds Bit 的 `product_id`、Morrishk 旧站 `snsii_product.id`、新平台 `pd_model.id` 之间如何建立唯一、稳定、可审计的对应关系？

**现状证据**

- Ds Bit 引擎侧 `Product.product_id` 是**文档内身份**，随一次解析产生，不是跨文档全局注册表；`requested_mpn` 与 `normalized_mpn` 目前可能被写成相同值（见项目记忆中的 PM-1..PM-5 缺口，尚未验收）。
- 旧站 `snsii_product`：`id` int(8)，`PartNumber` 唯一，`AUTO_INCREMENT` 已到 10,093,686（`mysql_schema_audit/01_schema.sql`）。
- 新平台 `pd_model`：`platform/db/migrations/20261116_0002__pd_model_core.up.sql`，仅 local/dev/staging。
- 同一 MPN 可能对应裸芯片与评估板（如 `AFE7950` vs `AFE7950EVM`），当前链路不能可靠区分 `identity_scope`。

**为什么必须决定**

- 映射表以 `dsbit_product_id` 为主键之一；如果 Ds Bit 没有全局稳定 ID，同步会出现"同一产品多行"或"不同产品合并"。
- 旧站与新平台两套自增 ID 不能混用，必须显式选择目标。
- MPN 归一规则不一致会导致漏匹配或错匹配。

**选项**

| 选项 | 内容 | 优点 | 风险 |
|---|---|---|---|
| A | Ds Bit 建全局产品注册表，`product_id` 由注册表签发（ULID） | 稳定、可跨文档 | 需要新设计与实现；Phase 1 前置 |
| B | 以 `mpn_norm + manufacturer + package` 组合作为业务键，`product_id` 仅文档内 | 无需注册表 | 同型号不同封装/批次会冲突；EVM 与芯片混淆 |
| C | 以 Morrishk 旧站 `snsii_product.id` 为主键反向映射 | 与现网一致 | 把 Ds Bit 绑死在旧站；新平台无法复用 |

**建议**

选 A，并同时明确 `identity_scope`（`DEVICE` / `BOARD` / `ONBOARD_DEVICE`）作为身份的一部分；`mpn_norm` 规则由双方共同冻结。若 Phase 1 无法先建注册表，则退化为 B + 强制人工审核，但必须记录为临时方案。

**影响**

产品 API、映射表、同步游标、撤回语义、审计链路。

## IQ-02 技术分类体系归属、初始种子与是否多体系

**问题**

技术分类体系（Technical Taxonomy）由谁维护？初始种子从哪里来？v1 是否只允许一个已发布体系？

**现状证据**

- Ds Bit 仓库内**不存在**任何产品分类模型或接口（主文档 §2.2）。
- `ParameterCategory` 是参数分组，不是产品分类。
- `DocumentType` / `SemanticDocType` / `DocType` / `Route` 是文档类型与流水线路由。
- Morrishk 旧站 `snsii_product_category` 是两级业务导航分类（`Pid=0` 为顶级），带 `Links` 唯一键与 URL 语义；新平台 `pd_category` 也是两级。
- 两套业务分类都**不能**直接当作技术分类。

**为什么必须决定**

- 分类 API 是一等子系统；体系归属决定 API 是 Ds Bit 提供还是 Morrishk 自建。
- 初始种子决定第一次同步是否有可用数据。
- 多体系会影响 `taxonomy_id`、产品边、映射表与 UI。

**选项**

| 选项 | 内容 | 优点 | 风险 |
|---|---|---|---|
| A | Ds Bit 维护单一技术分类体系，Morrishk 只读并映射 | 权威清晰 | Ds Bit 需要投入分类治理 |
| B | 按产品线拆多个体系（如 analog / power / logic） | 便于分线治理 | 产品跨体系归属复杂；映射翻倍 |
| C | Morrishk 自建技术分类，Ds Bit 只提供参数 | Ds Bit 负担小 | 分类与参数脱节；与其他消费方不一致 |

**建议**

v1 选 A，只允许一个 `PUBLISHED` 体系；初始种子由客户业务团队提供，**不得**直接把 `snsii_product_category` 名称导入为技术分类（名称相同不代表语义相同）。多体系留到 v2。

**影响**

§7 全部端点、`dsbit_category_mapping`、Morrishk 导航改造范围。

## IQ-03 `category_id` / `category_code` 的治理与生成规则

**问题**

`category_id`（ULID）与 `category_code`（稳定业务编码）由谁生成、何时生成、发布后能否修改？迁移/导入时如何保证不复用？

**现状证据**

- Ds Bit 无分类实现，无既有 ID 规则。
- Morrishk 旧站分类 ID 是 smallint 自增（`snsii_product_category.id`），`Links` 唯一；新平台 `pd_category.id` 为自增。
- 主文档 §7.2.4 已提出"ID 永不复用、改名不变、移动父节点不变"。

**为什么必须决定**

- `category_id` 进入映射表、产品边、审计与缓存；一旦复用会导致历史映射指向错误分类。
- `category_code` 用于外部映射；若允许改名，外部系统会失配。

**选项**

| 选项 | 内容 |
|---|---|
| A | `category_id` = ULID，创建即定；`category_code` 由治理流程分配，发布后冻结 |
| B | 允许 `category_code` 随业务改名，旧 code 进 `aliases` |
| C | 用层级路径（如 `ic.amplifiers.opamp`）作为 code，路径变则 code 变 |

**建议**

A。`category_code` 发布后不可改；改名只改 `name` 与 `aliases`。`external_codes` 承载外部系统编码，不反向污染 `category_code`。

**影响**

分类创建流程、导入脚本、映射维护成本。

## IQ-04 一个产品是否允许跨体系多个主分类

**问题**

同一产品在多个 taxonomy 下是否都允许一个 `PRIMARY`？同一 taxonomy 内是否严格只允许一个 `PRIMARY`？

**现状证据**

- 旧站产品只有 `BigCat` + `SmallCat` 两个字段，隐含"一个大类、一个小类"。
- 主文档 §7.2.3 暂定"同一 taxonomy 最多一个 PRIMARY"，标记为 `PROPOSED`。

**为什么必须决定**

- 影响产品边唯一性校验、分类页产品列表、面包屑与 SEO 落地页。
- 若允许多主，导航需要"哪个是默认"的规则。

**选项**

| 选项 | 内容 |
|---|---|
| A | 同一 taxonomy 内至多一个 `PRIMARY`；跨 taxonomy 各一个 |
| B | 全局至多一个 `PRIMARY`（跨体系也只一个） |
| C | 允许多个 `PRIMARY`，由 Morrishk 决定展示 |

**建议**

A。跨体系时允许每个体系各一个主分类，但 v1 只有一个体系，因此实际等价于"每产品一个主分类"。

**影响**

边的唯一性校验、`/products/{id}/categories` 响应、分类页排序。

## IQ-05 分类合并/停用保留期与 410 时机

**问题**

分类 `DEPRECATED` 后保留多久仍返回 `200`？何时改为 `410 CATEGORY_RETIRED`？保留期内 Morrishk 旧页面是否可以继续使用？

**现状证据**

- 现有系统无分类生命周期概念；旧站分类删除即不可用（无软删除字段）。
- 主文档 §7.5.6 建议 180 天，标记 `OPEN`。

**为什么必须决定**

- 保留期直接决定 SEO 页面可用时间与 301 规划窗口。
- 410 太早会导致已收录页面失效；太晚会让废弃分类长期存在。

**选项**

| 选项 | 内容 | 说明 |
|---|---|---|
| A | 180 天 | 与常见 SEO 迁移窗口一致 |
| B | 365 天 | 更保守，适合长尾流量 |
| C | 永久保留 `200` + `DEPRECATED` | 不产生 410，但数据永久膨胀 |

**建议**

A（180 天），且保留期内 Morrishk 可继续展示旧分类页，但不得新建产品关联。保留期从 `deprecated_at` 起算，日期可由客户按流量数据调整。

**影响**

分类 API 兼容语义、Morrishk 页面下线流程、301 计划。

## IQ-06 发布状态存储位置（Ds Bit 库 / 独立知识库）

**问题**

`PIPELINE_PASS` / `CONTENT_APPROVED` / `RELEASE_APPROVED` 与发布批次记录存在哪里？

**现状证据**

- Ds Bit 引擎**不连数据库**（`workbench/serve_parser.py:18`）。
- `src/icpdf/audit/__init__.py` 仅 6 行，未实现。
- 送审仓库 `07_prototypes/admin` 的三层闸门只是前端演示，无服务端记录。
- 新平台迁移中有 `sync_outbox`，但明确与 Ds Bit 无关。

**为什么必须决定**

- 发布状态是产品 API 的可见性开关；没有持久化就没有可信的 `RELEASE_APPROVED`。
- 审计要求"谁在何时改了什么"，必须落库。

**选项**

| 选项 | 内容 | 优点 | 风险 |
|---|---|---|---|
| A | Ds Bit 新建知识库（推荐 PostgreSQL），存产品/分类/版本/审批/发布 | 权威集中 | 需要 Ds Bit 首次引入数据库 |
| B | 复用新平台 MySQL 8 库 | 基础设施现成 | 新平台迁移禁止 production；职责混淆 |
| C | 存 Morrishk 库 | 接入简单 | 反向依赖，其他消费方无法复用 |

**建议**

A，且与解析产物（`runs/`）解耦：`runs/` 仍是不可变证据，知识库只存索引与状态。Phase 1 可先用 SQLite/PostgreSQL 本地实例，但表结构必须按生产设计。

**影响**

Phase 1 数据层、审计、同步源、撤回语义。

## IQ-07 内容审核与发布授权角色

**问题**

谁可以批准 `CONTENT_APPROVED`？谁可以批准 `RELEASE_APPROVED`？是否可以同一人兼任？是否需要双人复核？

**现状证据**

- Ds Bit 无审核/发布后端（`09_current_state_inventory/04-dsbit-workspace-inventory.md` DSB-21..DSB-25 全部 `NOT_FOUND`）。
- 原型中的 `contentRelease()` 只操作浏览器内 Demo 状态。
- Morrishk 侧无发布授权概念。

**为什么必须决定**

- 没有角色定义就无法实现权限模型、审计字段与审批流。
- 同一人兼任会使"三层闸门"退化为单人操作。

**选项**

| 选项 | 内容 |
|---|---|
| A | 内容审核员与发布负责人分离，发布需第二人确认 |
| B | 允许同一人兼任，但记录操作日志 |
| C | 发布由系统自动执行，仅内容审核人工 |

**建议**

A，至少 `CONTENT_APPROVED` 与 `RELEASE_APPROVED` 不能由同一账号在同一批次完成。角色清单需客户确认。

**影响**

Phase 2 权限模型、审批 API、审计表结构。

## IQ-08 证据公开范围与版权

**问题**

证据 API 是否对外返回 `raw_text`、`screenshot_reference`？是否允许 Morrishk 公开展示截图或原文？是否需要原厂授权？

**现状证据**

- `Evidence` 模型含 `raw_text`、`bbox`、`screenshot_reference`（本地相对路径）。
- 现有系统只在本地 `runs/` 目录，无在线服务。
- 主文档 §6.7 限定只给引用与短原文，公开下载需单独授权。

**为什么必须决定**

- Datasheet 原文与截图可能涉及原厂版权；公开转载有法律风险。
- 证据是"可信"卖点，但也是最大合规风险点。

**选项**

| 选项 | 内容 | 风险 |
|---|---|---|
| A | 只返回引用与短原文（≤500 字符），不提供截图下载 | 低 |
| B | 后台可见截图，公开页不可见 | 中 |
| C | 公开页可展开原文/截图 | 高，需法务确认 |

**建议**

A 为 v1 默认；B 作为 Morrishk 后台校对能力；C 必须单独法务评估，不在本设计范围。

**影响**

证据 API 响应、Morrishk 详情页展示、缓存体积。

## IQ-09 错误响应包最终形状

**问题**

业务 API 使用项目现有 `{code, message, data, request_id, meta}`，还是任务书建议的 `{"error": {"code": "PRODUCT_NOT_RELEASED", ...}}`？

**现状证据**

- `platform/docs/phase1/03-api-contract.yaml:9-14` 已定义统一包与 `code=0` 成功。
- `platform/web/src/lib/api/client.ts` 已有对应 `ApiError` 解析。
- 任务书建议的是 `error` 对象形状。
- Ds Bit 现有静态桩返回自定义结构（`x_local_static_stub`），不构成契约。

**为什么必须决定**

- 错误形状是客户端硬依赖；冻结后修改成本高。
- 两种形状并存会导致组织内 API 不一致。

**选项**

| 选项 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| A | 沿用 `{code, message, data, request_id, meta}` + `meta.error_key` | 与现有平台一致 | 与任务书建议不同 |
| B | 改为 `{"error": {...}}` | 符合任务书字面 | 与现有平台不一致，需改前端 |
| C | 双写（同时返回两套字段） | 兼容期平滑 | 冗余、易漂移 |

**建议**

A。`meta.error_key` 提供稳定字符串，`code` 提供稳定整数；映射见主文档附录 B。若 Reviewer 坚持 B，只需替换外层形状，不影响重试与降级语义。

**影响**

全部业务端点、Morrishk `DsBitClient`、测试断言。
