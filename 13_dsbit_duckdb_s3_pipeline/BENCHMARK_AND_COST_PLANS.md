本文件是主文档 §10 的展开。所有阈值、单价、耗时外推均为 `PROPOSED` 或**示例**，
不是承诺；未经 Stage B 实测的数字不得写进对外材料。

## 1. 阶段 A：单 PDF 端到端 Demo

### 1.1 目标

在**对象存储**上闭合一条链，并证明失败时不会产生「看似成功」的结果：

```
Raw 写入（条件写）
  → 协调器租约（generation）
  → Worker 解析
  → 产物上传（内容寻址）
  → Parquet 写入
  → Run Manifest v2
  → 协调器 COMMIT + committed.json
  → Eval（Gold v1 + 评估器指纹）
  → Catalog 快照（三级行数对账）
  → DuckDB 只读查询
  → verify_lineage
```

### 1.2 现状与缺口

| 环节 | 现状 | 本轮需补 | 证据 |
|---|---|---|---|
| Raw | `lake/raw_layer/<sha>` 本地目录 | 对象存储键 + 条件写 | `lake/_build_lake.py:107-133` |
| Parse | `parse_pdf()` 已产出 9 JSON | 上传 + Manifest v2 | `pipeline.py:136-188` |
| 协调器 | 无 | 单进程 + SQLite + 租约/提交 | 主文档 §5.2、`PIPELINE_ARTIFACTS.md` §9 |
| Parquet | 每 run 一个文件 | 批量缓冲 + 分区键 + part_manifest | `_build_lake.py:181-214` |
| Catalog | 本地 `.duckdb`，重建即删 | 快照目录 + manifest + 行数对账 | `_build_lake.py:355-449` |
| Eval | 单样本固定路径 | 按文档扩展 | `_build_lake.py:299-352` |
| S3 | 仅 `--local` 通过 | MinIO 开发验证 + **真实存储 C1–C10** | `_s3_connectivity_test.py` |
| Lineage | 本地通过 | 对象存储 + 快照 | `_verify_lineage.py` |

### 1.3 真实存储一致性（R6）

MinIO 只用于开发；Stage A 必须在**最终选型**存储上完成 C1–C10（清单见主文档 §10.1.1）：

| # | 检查 | 通过条件 |
|---|---|---|
| C1 | 条件写新键 | 首次 200；同键再写 412/409 |
| C2 | 并发同键条件写 | 恰好一个成功 |
| C3 | 无条件覆盖 + 版本化 | 产生新 VersionId，旧版本可读 |
| C4 | Multipart 中断 | 不产生半个对象 |
| C5 | Multipart 条件写 | 语义与 C1 一致，或有批准的 fallback |
| C6 | Versioning / VersionId | 历史版本可列出与读取 |
| C7 | HEAD / GET 回读 | ETag / 字节 / SHA 一致 |
| C8 | 一致性 | 写后立即可见，或记录等待窗口 |
| C9 | 错误码 | 412/409/403/404/5xx 映射正确 |
| C10 | 请求 ID | 可记录到 `attempt.json` |

### 1.4 验收清单

- [ ] 同一 PDF 两次执行：2 个 `run_id`、2 个 `lease_generation`，1 个 raw 对象，2 条 Run Manifest；
- [ ] 旧 generation 提交被 409 拒绝，且不写 committed 标记（N-12b）；
- [ ] 篡改 raw 1 bit：`verify_lineage` 失败，退出码非 0；
- [ ] 删除 manifest 但保留 eval：加载失败（`ManifestMissing`）；
- [ ] 快照中的 Parquet 被改 1 bit：校验失败，查询不返回少行；
- [ ] 2 run 共享 1 个 Parquet：Catalog 总行数只计一次（N-19）；
- [ ] 所有查询日志带 `snapshot_id`；
- [ ] N-01 / N-02 / N-07 / N-12b / N-14 / N-15 / N-19 通过；
- [ ] C1–C10 在真实存储上通过；
- [ ] 全程无对象被覆盖、无对象被删除（除临时目录）。

**通过后**才可进入 Stage B。Stage A 不产生任何质量结论。

## 2. 阶段 B：1000 份基准

### 2.1 样本设计（修订 R3）

v1.0 的筛选条件 `FetchStatus=1 且 HasTextLayer=1` 与「S5 无文本层 50 份」自相矛盾。v1.1 拆为两个独立池：

| 池 | 筛选 | 份数 | 用途 | 是否进入质量分母 |
|---|---|---|---|---|
| **P 可解析池** | `FetchStatus=1 AND HasTextLayer=1` | **950** | 解析质量、吞吐、证据完整性 | 是 |
| **Q 预期拒绝池** | 无文本层 / 扫描 / 加密 / 0 页 | **50** | 拒绝路径、错误分类 | 否（单独统计） |

P 分层：

| 分层 | 页数 | 份数 | 目的 |
|---|---|---|---|
| S1 | ≤ 20 | 280 | 常见短 datasheet |
| S2 | 21–50 | 280 | 主流 datasheet |
| S3 | 51–100 | 240 | 长文档、跨页表 |
| S4 | > 100 | 150 | 大件与超时风险 |
| 合计 | — | **950** | — |

抽样规则：

- P 与 Q 各自独立按 `sha256` 排序后等距抽样；
- 记录抽样种子、池标记与完整 `task_id` 列表；
- 不挑选「已知解析成功」的样本；
- 允许同一 PDF 的重复输入进入 P，用于测重复率；
- Q 的 PDF 不进入「可解析率」与「有效输入处理失败率」的分子/分母。

### 2.2 逐件测量项

| # | 指标 | 采集方式 |
|---|---|---|
| 1 | 墙钟耗时（s） | `perf_counter` 包裹整任务 |
| 2 | 解析耗时（s） | Worker 子进程自报 |
| 3 | CPU 时间（user+sys） | `resource.getrusage`（POSIX）/ `psutil`（Windows） |
| 4 | 峰值 RSS（MB） | 子进程采样（100 ms） |
| 5 | 临时磁盘峰值（MB） | 工作区 `du` 采样 |
| 6 | PDF 字节 | Raw 元数据 |
| 7 | 9 个 JSON 产物字节 | Manifest `artifacts[].bytes` |
| 8 | Parquet 字节 | `part_manifest.json` |
| 9 | 上传字节 / 请求数 | S3 客户端计数器 |
| 10 | 页数 / 表数 / 候选数 | Manifest `counts` |
| 11 | 重试次数 / 错误类 / `lease_generation` | 任务事件 |
| 12 | 证据完整率 | Parquet 查询 Q4 |
| 13 | 血缘校验结果 | `verify_lineage` |
| 14 | 查询耗时（Q1–Q8） | 查询日志 |
| 15 | 池标记（P/Q） | 批次清单 |

### 2.3 汇总口径（修订 R3）

| 指标 | 分子 | 分母 |
|---|---|---|
| 预期输入拒绝率 | Q 中按预期 `INVALID_INPUT` | 50 |
| 有效输入处理失败率 | P 中非 `SUCCEEDED` | 950 |
| 基础设施失败率 | P 中 `OBJECT_STORE_*` / `NETWORK_*` / `DISK_FULL` | 950 |
| Parser 异常率 | P 中 `PARSER_EXCEPTION` | 950 |
| 重试率 | P 中 `attempt > 1` | 950 |
| 重复率 | `1 - unique_sha256 / P_inputs` | — |

- 分位数：P50 / P90 / P95 / max，按分层与总体分别给；
- 吞吐：`成功文档数 ÷ 总墙钟小时`，同时给「每机」与「全批」；
- 单件成本：`阶段总成本 ÷ 成功文档数`；
- 所有比率必须给分子分母，不只给百分比；
- **禁止**把 Q 的预期拒绝计入「有效输入处理失败率」。

### 2.4 通过门槛（PROPOSED，待确认）

| 项 | 建议阈值 | 不通过处理 |
|---|---|---|
| 血缘校验 | 100% | 停止，修链路 |
| 证据完整率 | 100% | 停止，修解析/落库 |
| 三级行数对账（Q8） | 0 差异 | 停止，修写入 |
| **有效输入处理失败率（分母 950）** | ≤ 2% | 分析错误类；不可重试错误需逐类解释 |
| 基础设施失败率（分母 950） | ≤ 1% | 分析存储/网络 |
| Parser 异常率（分母 950） | ≤ 1% | 修代码后重跑 |
| 重试率（分母 950） | ≤ 5% | 分析存储/超时 |
| Q 预期拒绝率（分母 50） | ≥ 95% | 检查拒绝路径；不按失败计 |
| P95 解析耗时 | ≤ 超时阈值的 50% | 调整超时或并发 |
| Q1 单 run 链路查询 | ≤ 5 s（1000 份规模） | 检查分区与文件数 |
| Q3 批次聚合 | ≤ 10 s（1000 份规模） | 检查文件大小与字典编码 |
| 单件存储（不含 PNG） | ≤ 8 MB | 检查产物是否可压缩 |
| 最大 RSS | ≤ 单机内存 70% / 并发数 | 降并发 |

> 这些阈值不是行业标准，是本项目用于决定「能否进入 3–5 万试跑」的工程门槛；
> 需要 Reviewer 明确同意或修改（OD-09）。

## 3. 阶段 C：3–5 万份试跑

### 3.1 拓扑

| 组件 | 规格 | 数量 | 说明 |
|---|---|---|---|
| Worker | 8 vCPU / 16 GB / 本地 NVMe 200–500 GB | 2–4 | 与现有 G0 环境同规格参考 |
| 协调器 | 2 vCPU / 4 GB / 本地 SSD | 1 | 单进程 + SQLite WAL；不是数据库服务器 |
| 对象存储 | 同区、私有、版本化 | 1 桶 | 不与计算跨区 |
| 分析节点 | 8 vCPU / 32 GB | 1 | 构建快照；可与 1 台 Worker 复用但在批次间隙运行 |

### 3.2 并发策略

1. 每机起始并发 4；
2. 每 100 份统计一次 P95 耗时与峰值 RSS；
3. 若 RSS > 内存 70% 或 P95 > 超时阈值 50%，每次降 1，最低 2；
4. 若 P95 明显低于阈值且 RSS < 50%，可每次升 1，最高 = vCPU；
5. 并发调整必须写入批次事件，便于复盘。

> 任务分配由协调器动态发放租约；**不使用静态分片**。扩容只需新增 Worker 并注册，不需要重新分片。

### 3.3 资源规格选择依据

| 资源 | 依据 | 待实测 |
|---|---|---|
| 8 vCPU | 解析单进程 CPU 密集；并发 ≈ vCPU | 并发有效率 |
| 16 GB | 工作台 2 vCPU/2 并发的经验；峰值 RSS 未测 | 单进程峰值 RSS |
| NVMe 200–500 GB | 单任务临时空间 + Parquet 缓冲 | 单件峰值磁盘 |
| 同区存储 | 避免跨区 RTT 与出口费 | 同区延迟 |

### 3.4 容量估算（示例，不是承诺）

假设（全部待 Stage B 替换）：

- 单件 PDF 平均 2 MB；
- 单件 JSON 产物 4.65 MB（V101 实测：1.22 MB PDF → 9 个 JSON 合计 4,651,886 B）；
- 压缩后按 1/5 计 ≈ 1 MB；
- 单件 Parquet 28 KB（`lake` 实测 28,332 B）；
- 3–5 万份取 40,000。

| 项 | 计算 | 结果 |
|---|---|---|
| Raw PDF | 40,000 × 2 MB | ≈ 76 GB |
| JSON 产物（压缩） | 40,000 × 1 MB | ≈ 38 GB |
| Parquet | 40,000 × 28 KB | ≈ 1.1 GB |
| 快照与日志 | — | ≈ 5 GB |
| **合计** | — | **≈ 120 GB** |

> 若 PDF 平均 5 MB，Raw 约 190 GB，合计约 235 GB。桶容量按 300 GB 规划并留 2 倍余量。

### 3.5 断点续跑

- 协调器 SQLite 保存 task / lease / commit；每 30 s 检查点；
- 每任务终态写 `control/tasks/<task_id>/final.json`；
- 每 30 s / 100 条事件上传 Worker 事件日志；
- Worker 重启后向协调器重新注册；已提交任务跳过；未提交任务按租约过期重派；
- 批次级检查点：每 1000 份构建一次快照，崩溃后不必从头恢复；
- 恢复后先跑 `verify_lineage` 抽样，再继续。

### 3.6 数据校验

| 层 | 方法 | 频率 |
|---|---|---|
| Raw | 抽样重算 SHA-256 | 每批 1% |
| Parse | Manifest 必填字段 + 指纹一致 | 全量 |
| Parquet | 行数与 manifest 对账 | 每批全量 |
| Eval | Gold 文件哈希 + 评估器指纹 | 每批全量 |
| 血缘 | `verify_lineage` | 每批全量 |
| 人工 | 参数名/值/单位/条件/归属 | 每批 ≥ 500 件（技术方案 §7.10） |

### 3.7 停止与回滚条件

| 条件 | 动作 |
|---|---|
| 失败率 > 5% 持续 30 min | 停止接新任务；保留现场 |
| 指纹漂移（同批次出现两个 `parser_fingerprint`） | 立即停止；该批次作废 |
| 磁盘 > 90% 或对象存储 5xx 持续 10 min | 停止；退避后重启 |
| 任一血缘校验失败 | 停止；定位到具体 run |
| 单位成本 > 预估 120% | 停止；重新核算后再决定 |
| 发现 raw 被覆盖/删除 | 立即停止；冻结批次；人工取证 |

**回滚**：

1. 停止 Worker（不再接单）；
2. 不发布新快照；
3. 保留全部对象与事件；
4. 写批次墓碑（`status=tombstoned`，原因、时间、操作者）；
5. 如需重跑，使用新 `batch_id` 与新 `attempt`；**不删除**旧数据。

## 4. 全量 568,830 份：只能外推

### 4.1 公式

```
预计机时 H = N × mean_parse_seconds / (3600 × concurrency_effective)
预计日历时间 D = H / (worker_count × 24 × utilization)
其中：
  N = 568,830
  concurrency_effective = 并发数 × 有效率（0–1，Stage B 实测）
  utilization = 每日有效运行占比（建议 ≤ 0.8，留维护与重试）
```

### 4.2 外推示例（假设值，不是承诺）

| 假设 | 值 | 来源 |
|---|---|---|
| `mean_parse_seconds` | 20 s | 工作台文档记录 16.8 / 22.3 s（21 页 / 1.22 MB）；**不是 568,830 份的均值** |
| 并发 | 4 | 设计值 |
| 有效率 | 0.7 | 假设，待实测 |
| Worker 数 | 4 | 设计值 |
| 利用率 | 0.8 | 假设 |

计算：

```
concurrency_effective = 4 × 0.7 = 2.8
H  = 568,830 × 20 / (3600 × 2.8) ≈ 1,129 机时
D  = 1,129 / (4 × 24 × 0.8) ≈ 14.7 天
```

**必须同时披露的偏差来源**：

- 样本只有 21 页 / 1.22 MB，全量分布未知；
- 峰值 RSS 未测，并发 4 可能不成立；
- 失败重试、人工审核、对象存储限流未计入；
- 大件（>100 页）可能显著拉高均值。

因此对外只能给「约 X–Y 天（基于假设）」并附假设表；**不得**给单一日期或固定金额。

## 5. 成本估算方法

### 5.1 公式

```
月成本 C =
    Σ_i (worker_hours_i × price_vcpu_hour)          # 计算
  + storage_GB_month × price_GB_month               # 存储
  + (put_requests + get_requests) / 1000 × price_1k # 请求
  + egress_GB × price_egress_GB                     # 出口
  + analytics_hours × price_analytics_hour          # 分析节点
  + ops_cost                                        # 人力，单列

单件成本 = C ÷ 当月成功处理文档数
```

### 5.2 占位单价（示例，不是报价）

| 项 | 占位值 | 说明 |
|---|---|---|
| `price_vcpu_hour` | $0.13 / 8 vCPU 机时 | 约等于 $96/月 ÷ 730 h；实际以云商账单为准 |
| `price_GB_month` | $0.02 / GB-月 | Spaces / OSS 量级；实际以云商为准 |
| `price_1k` | $0.005 / 千次 | 请求费；不同厂商差异大 |
| `price_egress_GB` | $0.01 / GB | 同区读取通常不计；跨区/公网另计 |
| `price_analytics_hour` | $0.20 / 小时 | 8 vCPU / 32 GB 量级 |

### 5.3 3–5 万试跑示例

假设处理 40,000 份、4 台 Worker、总机时 400 h、存储 120 GB、请求 100 万次、无公网出口：

| 项 | 计算 | 金额（示例） |
|---|---|---|
| 计算 | 400 × $0.13 | $52 |
| 存储（首月） | 120 × $0.02 | $2.4 |
| 请求 | 1,000 × $0.005 | $5 |
| 分析节点 | 50 × $0.20 | $10 |
| **合计** | — | **≈ $69** |
| 单件 | $69 ÷ 40,000 | **≈ $0.0017 / 份** |

> 该数字只用于说明方法；实际成本受 PDF 大小、重试、查询频率、跨区流量影响。
> 对外报价必须由财务/云商账单确认，不得引用本文示例。

### 5.4 敏感性

| 变量 | 变化 | 对成本影响 |
|---|---|---|
| PDF 平均大小 | 2 MB → 5 MB | 存储约 ×2.5 |
| 解析耗时 | +50% | 计算约 ×1.5 |
| 重试率 | 5% → 20% | 计算约 +15% |
| 跨区读取 | 同区 → 跨区 | 查询延迟数十倍；出口费另计 |
| 查询频率 | 每天 100 次 → 1000 次 | 计算/请求费上升，需物化缓存 |

### 5.5 不摊入单件成本的项目

- 人工审核（按样本计，单列）；
- 一次性架构与开发；
- 数据治理与合规；
- 失败批次的返工；
- 冷备/归档的长期存储（按保留策略另算）。
